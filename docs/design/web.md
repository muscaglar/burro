# Burro website: design

Status: design for the first build, 2026-09-23. The foundation of `apps/web` is built: the API types and client, the recorded answers, the tokens, the shell, and the methods, sources and accessibility pages. So is the search page, with its chips, its settings, its result cards and its map. So are the page of an area, the comparison, sharing, the sitemap and the robots file. The parts were then put together and gone over as one website: the answers were recorded again from the API as it then stood (engine 1.3.0; it moved three times while this was done, from 1.1.0, and the recordings followed it each time), every built page was read, one whole visit was walked against the service's own answers, and the website was answered with what it did not expect. What each of these settled is written in where it applies. It has since been run in a browser once, and read by two reviewers. The browser showed four things no test could: the map drew nothing, a button lay over the map, there was no icon, and a strength was given as a trade-off. The reviewers found nineteen more. What was put right is written in where it applies, each with the test that would have caught it. It was then walked through in a browser against the service itself, at the width of a phone and of a desk, by mouse and by keyboard. That found nineteen things more, of which the gravest was that a sentence could lose its budget and its workplace and the page ranked as if it had read them. What the website could put right is written in where it applies, and what needs the service is in section 13, gaps 17 to 22. Section 9 ends with the checks that must be made by hand, because no test can make them. The README says what to type to see the website in a browser.

This is the single source for the website in `apps/web`. It applies [PLAN](../PLAN.md) sections 4, 5, 8 and 9, ADRs [0002](../adr/0002-deterministic-core.md), [0005](../adr/0005-raw-prompts-are-never-stored.md), [0006](../adr/0006-rank-places-not-residents.md), [0008](../adr/0008-package-sources.md) and [0011](../adr/0011-nothing-is-kept-for-a-search.md), and [the contract](contract.md) sections 4, 5, 8 and 9. Where this document and the contract disagree, the contract is right and this document changes. Three people build three parts: section 11 says who owns what and where the parts meet. Section 13 lists what the contract does not yet give the website, and what the website does until it does.

## 0. Terms and the three rules

| Term | Meaning |
|---|---|
| Route N | The route with that number in contract section 9.2 |
| A type in `code` | The schema of that name in `contracts/openapi.json`, generated into `src/lib/api/schema.d.ts`. Never written by hand |
| API text | A string the API returned: a sentence's `text`, `notice_text`, an error's `message`, a fact's `label`, or a value in its `slots` |
| Site copy | Words kept in `src/content/`. They name controls, states and codes. They never hold a number or a proper noun about a place |
| The store | The one object in memory that holds a search (section 5.3) |

1. **Words about a place are API text.** The website lays API text out. It does not write, join or reword it. It formats no number that a fact's `slots` hold already formatted. It never prints a percentile: `slots.standing` says where a figure sits, and is literally true.
2. **The spec on screen is the last spec the API returned.** The website builds edits, never specs.
3. **What a person types stays in the box it was typed in, and in one `POST` body.** Section 10 lists everything else that is held, and where.

## 1. The first thirty seconds

The person has never been to London and arrives at `/` from a link. "May take" is a budget on broadband to a service in London. None has been measured against a service in London.

Wide screens, 60rem and over, put the list beside the map. Narrower ones stack them under three tabs: List, Map, Table.

- **The banner** is site copy, shown on every page while `meta.synthetic` is true, at build or in any answer since: "This is made-up test data. The city, its places and every figure are invented. Nothing here describes a real place." It cannot be closed.
- **The line under the box** reads: "What you type is sent to Burro to be read, and Burro does not keep it. If a language model reads it, the model's provider may keep it for up to 30 days, or longer if it is flagged." It promises no more than ADR 0005 does, and a test holds it to that.
- **The examples** hold no proper noun, so none can go stale when a release changes. They are for a first search. Once a search is open they go, because an example pressed then would be added to it: "Buying a terraced house" on top of "leafy and quiet". They come back with "Start again".
- **What Burro says of a search stands directly under the box.** In a browser, pressing Search changed nothing on screen: on a phone what was understood began a screen and a half down, under the examples, the tenure and the place field. Now nothing but the box's own line about words stands between the box and what Burro says. Measured on a phone 390 wide and 844 high, after the first example: the line that says what happened at 711 px, the chips at 771 (they were at 1,326), the first result at 1,824 (it was at 2,100 or more). Before a search the page is as it was: the examples, then the tenure and the place, then the chips, which say what a search starts from.
- **Once a search is open the box says that what is typed is added to it**, and "Start again" stands beside Search. It empties the box, puts the focus in it, and goes back to the defaults the API served. The areas chosen to compare are left as they are.

## 2. Pages and routes

One environment variable says where the API is: `NEXT_PUBLIC_BURRO_API_URL`. The browser calls that address itself. The website has no route handler, no server action and no middleware, so nothing a person types passes through the website's server. The server calls the same address only while it builds a page, and only routes 4, 5, 6 and 11. With the variable unset a build reads the recorded responses of section 11, which is how a build runs where no API can, and the browser's client answers `not_configured` without sending anything. `src/lib/api/config.ts` reads the variable, `next.config.ts` reads it for the content security policy, and a test fails if any other file does. A second variable, `BURRO_SITE_URL`, says where the website itself is. It is read on the server, in `src/lib/indexing.ts` and nowhere else, and is used for what a search engine is told and for nothing else.

- `[city]` is `synthetic` for ids that begin `syn` and `london` for `lon`. `src/lib/city.ts` holds the pair and nothing else does.
- **One rule says whether anything may be indexed**, and it is in `src/lib/indexing.ts`: a page may be indexed only when the release is real and the website knows its own address. The address comes from `BURRO_SITE_URL`, read on the server and in that one file. While the rule says no, every page carries `noindex, nofollow`, every answer carries the header `X-Robots-Tag: noindex, nofollow`, the robots file names no sitemap, the sitemap lists nothing, and an area's page has no canonical address and no structured data. **The robots file never keeps a crawler out.** One that is kept out never fetches a page, so it never reads that the page asks to be left out, and may still list the address of a made-up place from a link it found elsewhere. The header says the same for what is not a page and can carry no `robots` of its own, such as the robots file and the icon. It is worked out when the website is built, from the same rule, and a release that cannot be read then is taken for one that may not be indexed. When it says yes, every page may be read, the sitemap lists the search, the three pages about the website and one page for each area from route 4, and an area's page carries its canonical address and its structured data. A comparison and the page a share opens are one person's: they carry `noindex`, in the page and in the header, whatever the rule says, and the sitemap never lists them. A test asks all of these at once and fails if any two disagree.
- **What an area's page tells a search engine is what its `area` fact says**, and no more. The title is the name and the borough. The description names them and then describes the page, not the place. The structured data is a `Place` with its name, its address on the website, and the borough as the place that holds it. It holds no figure and no coordinates: no fact holds where an area is. It is written into the page as the text of a script, with every `<` written as its escape.
- "Hourly" is a revalidation of 3,600 seconds, the `max-age` the API sends for routes 4, 5, 6 and 11. If an answer in the browser names a `release_id` other than the one the page was built on, the browser fetches routes 4, 5 and 11 again and uses those. It does so beside the search and never in its way: reading the form again changes the form and the names of the areas, and takes nothing from the cards. It is asked for once at a time. If it cannot be read, or the boundaries cannot, the next answer that names the release asks again. A browser may also answer routes 4, 5, 6 and 11 from its own cache for that hour (section 13, gap 15).
- A share is made in `SharePanel`, which opens in place under the heading of the results once there is a ranking. It says what the link will hold, offers "Share the exact places" unticked, sends route 9 with the spec the store holds, and shows the link `/s#share_id` in a field to copy from, with the stored spec as chips. If `coarsened` is true it says the ranking may differ a little. If nothing was replaced and the box was left unticked, it says that no place needed replacing, because each is a station or a district already: it said "The link holds the places as you named them", which read as if the choice had been ignored. A link is shown only for the search it was made of: change the search, and the link goes. The session keeps the link that was last made, so that it is still there when the person comes back from the page of an area.

What building the area page, the comparison and sharing settled:

- **The session.** The search that is open and the areas chosen to compare are held by `SessionProvider`, which the shell of every page holds. The shell stays while one page gives way to the next, so both are still there after a link inside the website is followed. Loading a page afresh, or closing the tab, loses both. Nothing is written anywhere: section 10 stands.
- **The areas to compare are not part of the search.** They are chosen from an area's page as well as from a result, and an area's page holds no search. The session holds them as each area's id, slug and name. Starting the search again leaves them as they are.
- **The address of a comparison decides what is compared.** The tray builds the address, and the page puts the areas of its address in the tray, so going back to choose others starts from what was compared.
- **A comparison shows a fact's slots and never a cell's numbers.** A cell of route 7 holds `value`, `percentile`, `utility` and `contribution` as numbers. The page shows the slots of the fact the cell cites, as the API formatted them, and the contribution as "Adds 23 of 100 to the fit", rounded down. It never shows `value`, which is the same figure unformatted, nor `percentile`, nor `utility`.
- **Where an area stands is shown only from a search.** Route 7 gives no score. When a search is open and its ranking is of the spec that is sent, each ranked area shows its rank and its fit from that ranking. With no search open it shows neither.
- **The table is stacked on a narrow screen.** Under 60rem each row becomes a block: the thing that counts, then each area under its own name. It is one table in the page either way, and every row and cell says its role, so that a browser which forgets a table when it is laid out as blocks is told again.
- **An area's page gives the source under each fact, not behind a button.** `SourceLine` writes out what `SourceNote` opens, because the page must read with scripts off.
- **Every feature of the release has a row on an area's page.** One the area has no figure for says "No figure in this data", and shows no figure, no comparison and no source.
- **What is served with no fact behind it is not shown.** Whether a station is step-free, an area's other names, its coordinates, a feature's coverage and a tag's raw score are all in route 6 and in no fact, so none has a source or a date (section 13, gap 9).
- **Cost on an area's page is a row for each kind of home**, as `FactRow` lays a `cost` fact out. `CostRange` and its bar are for a result card, where there is one kind of home and a budget to mark on it.
- **Opening a share leaves the search that was open alone until the share has come.** If the link leads nowhere the page says so in the API's words, and the search before is as it was. When the share comes it takes the place of the search whole: no question, no name and no edit of the search before is carried into it.
- **A link that is already open is not opened again.** The store keeps the id of the share a search came from, so coming back to the link does not put the stored spec over what the person has changed since.
- **What follows the `#` is sent only if it is an id.** Anything else is never sent, never shown and never put in a link. The page says the link is not one, in fixed words.
- **A share whose release has moved on reads the form again first**, so that it is drawn with the names and the limits of the release that ranked it. The line that says a share is stale names the release its ranking came from, which the answer names, and not the one the page was built on.

## 3. Every state of the search page

`phase` is one of `empty`, `interpreting`, `results` and `refining`. The other rows are conditions that sit on a phase, and several can hold at once. The prompt box, the settings and the table of all areas are on screen in every state.

| State | Entered when | The person sees | The person can |
|---|---|---|---|
| Empty | No search yet | Step 1 of section 1. The settings are closed and hold `defaults.rent` | Type, pick an example, add a place, open the settings and search by hand, browse areas |
| Interpreting | Text was sent to route 1 | Step 3. The text stays in the box. It lasts until the ranking of the words is in, so the chips may already be drawn from the words that were read | Stop, which aborts the request and puts the search back as it was when the sentence was sent: the spec, its chips, and what was read before. The list was never changed. The text stays in the box |
| Results | Route 2 answered with at least one `ranked` | Chips, list, map. One line of site copy for each `UnmetCategory` in `unmet`. One line for each `RejectReason` in `rejected`, beside the chip it concerns, or under the chips when it has none | Read, open sources, refine, compare, share, hide an area, open an area page |
| Refining | A chip, a control or a second sentence changed something | The last results, marked `aria-busy`, under the words "Working out the ranking again". They are not dimmed: at 70% the muted text, the links and the edges all fall below the contrast of section 8. The control touched shows its new value. When the answer comes every control is redrawn from the returned spec, and the live region says how many areas changed place | Keep editing. The latest request wins: an older answer is dropped by its sequence number |
| Clarifying a place | `clarify` is not empty | Results for everything else that was read, because the edit with no id was rejected and the rest applied. | Nothing matches | Route 2 answered and `ranked` is empty | "No area passes every limit you set." A count for each `FilterReason` and `UnrankedReason`. One button for each firm limit in the spec: make the budget flexible, make a journey flexible, show hidden areas. The map hatched, and the table with each area's reason | Press a button, which sends that one edit |
| Nothing read | `status` is `off_topic`, or no `applied` edit has `changed` true and `clarify` is empty | `notice_text` if there is one, else one line of site copy. The line for `other` in `unmet` is left out, because the one line has said it | Say it another way, or use the settings |
| Read in part | `unmet` holds `other`, and something was read | Directly under the box, drawn as a notice and not as small print: "Burro read only part of what you typed, and the ranking leaves the rest out." While the box still holds what was sent, a button, "Show the part that was not read", which selects that part in the box. Results for what was read | Say the rest again in shorter sentences, or use the settings |
| Degraded to a form | `degraded` is true, or route 1 timed out, answered 5xx, or answered what is not the API's | "Your words could not be read just now. The settings below do the same job." | Burro not reached | A request for route 1 could not leave, or the website holds no address for the API | The error block: "Burro could not be reached." It does not say the words could not be read, and the settings are not opened: they could not reach it either | "Try again" sends the same text. "Start again" |

The block goes when the next sentence is sent |

What building the search settled:

- **An edit is never lost to a call that is out.** Edits made while a call is out are kept in the store as `pending`. Each new edit is sent with the last spec the API returned and every edit still pending, in the order they were made, and the older call is stopped. The website still applies none of them. When an answer comes, `pending` is emptied. When a call fails, `pending` is kept and "Try again" sends it again.
- **A control moved while a sentence is being read waits for the reading.** Its edit goes with the spec the reading returns. If the reading fails or is stopped, the edit is sent with the spec as it was.
- **Nothing read and nothing changed are told apart.** Words that were read into edits that changed nothing, such as "renting" said to a renter, get "That changed nothing. Your search already says it." and not "could not be read". The line goes as soon as a control is used.
- **The settings can be ranked as they stand.** While there is no ranking, the settings hold a button, "Rank with these settings", which sends route 2 with the spec and no edit. It is how a person sees the defaults ranked without typing.
- **Reasons must be for the ranking on screen.** Route 2 returns a `spec_hash`, and route 3 returns none, so the website keeps the hash of the spec it sent with the reasons that came back (section 13, gap 14). A hash is of the spec alone, and is the same on every release. So the release and the engine each answer names are kept with what the answer brought: the reading, the ranking, the reasons, each profile and each fact. A card shows reasons only when they are for the same spec as the ranking and the same release and engine made both. If they are not, as when the release moved between the two calls, route 3 is asked once more. Reasons that are still another release's are never shown: the cards say the reasons could not be loaded, and "Try again" ranks again.
- **What is on screen is of the release that made the ranking.** When a ranking comes from another release or engine than the one before it, the facts, the profiles and the reasons the other made go, and are asked for again. Reading the form again takes nothing away, whenever it comes: before this, a form that came after the reasons and the profiles emptied every card, and nothing asked for them again. A profile a browser answers from its own cache may be of the release before. It is shown, with the release that made it kept beside it, and is asked for again once when the ranking's release changes. A fact of the ranking's release is never given up for one of another.
- **The foot of a card names the release and the engine that made the ranking**, from the ranking's own answer, and not those the page was built on.
- **Reasons or a profile that cannot be loaded are never met with silence.** The failure is kept whole, with the API's `message` and the `X-Request-Id`. The card says what it lacks, and the error block says why, with "Try again", which ranks again and asks for what is missing. Only the profile that failed is asked for again. It does not say the results were not updated, because they were. If the browser was offline, the offline line says so, and they are asked for again when it is back.
- **Stop puts the search back.** Reading a sentence replaces the spec before its ranking is in, so that the chips can be drawn at once. The search as it was when the sentence was sent is kept until that ranking comes. Stop puts it back, so the chips never say one search over the ranking of another. A sentence sent before the last one was ranked is undone with it. An edit made meanwhile is not undone: it is sent with the spec that was put back. Reasons that came for the ranking that was stopped are let go.
- **One failure is shown in one place.** A refusal of the text is under the box. A reading that failed is the "could not be read" line, with "Try again". A reading that never reached Burro is the error block. Offline is the offline line. Anything else is the error block.
- **The line that says what was ranked names the first result the page has a name for.** An area the page was not built with has none. With a name for none, the line gives the count alone.
- **An answer that lacks what the contract requires is not read.** The client checks that the `data` of an answer holds every field the contract requires of that route, by name, from a list generated from the contract (`src/lib/api/required.ts`). One that does not is `unreadable`, and is said as any failure is. Before this, an answer with nothing in it left the page waiting for ever. A field or a code the website does not know is let through and breaks nothing: a line it has no words for is left out.
- **A ranking that fails leaves the list the reasons it has.** The reasons for a sentence are asked for beside its ranking, and may come first. Reasons that are for a ranking that has not come wait in the store, as `explanationsAhead`, while the reasons on screen stay. When that ranking comes they are its reasons. If it fails, the ranking on screen keeps its own. Found while building the comparison: before this, a second sentence whose ranking failed left every card waiting for reasons that never came.

What a browser showed, which no test had:

- **A part that was not read is said beside the box, and shown in the box.** A sentence of three parts gave one chip, and 21 areas were ranked as if all three had been read. The one sign was a grey line under the chips, off the screen, that did not say which part. The reader is the API's, and reads a sentence only when it knows every word in it (section 13, gap 19). What the website can do is say it where it is seen, and show which part. Route 1 says which words each edit rests on, as offsets (`rests_on`). A sentence no edit rests on is a part that was not read. `src/lib/search/unread.ts` finds those, ending a sentence where the reader ends one (contract 8.2), and the box selects the part: the words stay in the box, and are written nowhere else on the page. With two parts or more, each press selects the next. Where the words stand is known for the text that was sent, so the button goes as soon as the box is changed.
- **A budget that goes is said to have gone.** A change of tenure takes the budget off, because a rent is not a price (contract 5.3, rule 5). In a browser £1,700 a month vanished without a word when the next sentence said "Buying". The line that says what happened now says that the budget was taken off, and why.
- **How many areas changed place counts the areas that moved.** When a list of 20 became a list of 15 the page said "21 areas changed place". An area that went, or came, moves no other. The line says how many went or came, and then how many of the rest stand elsewhere than they did: "15 areas ranked, 6 fewer than before. 2 of the rest changed place."
- **The focus is never left on nothing.** It was, in four places. A chip that is removed gives the focus to the chip beside it. A question that is answered, or left out, gives it to what Burro understood. A pin that is pressed takes the focus itself: the map takes a press for its own, and the pin never took it. Closing the card of an area gives it back to the pin, or to the map. A button that may be pressed until it does nothing, as "Make the link", "Clear the budget" and the ends of a slider are, says that it is off (`aria-disabled`) and is never switched off: a button switched off while it has the focus loses it.

- `WeightSlider` is a range input from 0 to 1 in steps of `weight_unit`, shown as 0 to 100. What 0 and 100 mean is drawn where it can be seen: once for each group of sliders in the settings, and under a slider that stands alone, as in a chip. Beside it sit a minus and a plus button that move it by `weight_step_small`, and a number field. It sends on release, or 150 ms after the last key or the last press of a button, never while it is dragged. A number typed in is sent when the field is left, or on Enter.

- **The features are headed "What counts nearby"**, and not "What you want nearby": transport noise and nitrogen dioxide stood under that, and neither is wanted.

- **What is being typed is the person's until it is sent.** An answer that comes while a number is half typed, or in the moment before a slider's change is sent, leaves it alone: it may be the answer to a sentence that was being read, and the digits typed next would be joined to its number and sent. Once a value is sent, the control shows it until the next answer, and then shows what the API returned.
- **A value is held against what is on its way.** A control sends nothing when the value it is set to is the one it already stands at. What it stands at is the value it last sent, while that waits for its answer, and the spec's after. So a slider moved to 70 and back to 50 before the answer sends both, and the API, which applies edits in order, ends at 50. Before this the switch sprang back on when the answer came, and "ignore the high street" was shown as a wish for one.
- The kinds of home that go with each tenure are held in `src/content/settings.ts` (section 13, gap 8).

Under the chips one line says who read the words: "Read by AI. Check what it understood." when `interpreter` is `claude`, "Read without AI, by fixed rules." when it is `rule`.

**Everything that explains the chips is drawn where it can be seen.** It was written, and then kept for a screen reader alone. The heading is small and visible, and says what the chips are: "What a search starts from" while the spec is one of the two defaults the API served, "What Burro understood" once words have been read into a search, and "What this search holds" for a search made with the settings or opened from a link. A place added with a control is marked in every part its edit did not state.

**"The slowest journey" is not what `slowest` means.** It is the journey worth least against its own limit, which need not be the one that takes the most minutes (contract 6.4). The settings, the chip, the card and Methods all say "the journey that does worst against its limit".

### 5.3 How typing and controls stay in step

One store holds the search. It is a React context over a plain object, with no library. `state.ts` holds the object and the one pure function that moves it on. `store.ts` holds it in memory and hands it to the page. `flow.ts` holds what a person can do, as the calls each makes. The session keeps the store while the tab is open (section 2), so a page that is not the search page reads the search with `useOpenSearch`. Beside the fields below, the store holds `pending` (edits not yet answered), `refused` (edits a control sent that the reducer rejected), `answers` (a count of the answers that leave no edit waiting, against which a control holds what it was set to), `untouched` (true until an answer changes the spec), `kept` (the search as it was when the sentence being read was sent, for Stop to put back), `settingsOpen` and `settingsByPage` (true while the settings are open because the page opened them and the person has not used them), `tenureSaid`, `budgetWent`, `rankedBefore` (how many areas the ranking before this one ranked), and what could not be loaded, each with the failure that says why.

`answers` does not move when a reading comes while an edit waits. The edit has not been answered, so the control that was moved keeps showing what it was set to until the ranking comes. A control nobody has touched is drawn from the spec whenever the spec changes.

| Score | The band | The band's range in the legend, in figures. "Fit 78 of 100" in the pin's name, the map card and the table |
| Filtered, not ranked | | The pattern, and the reason in words in the map card and the table |
| Selected | | The 3 px outline, a larger pin, and `aria-current` on the card and the table row |

- **In step.** `selectedId` and `hoveredId` are in the store. Hovering or focusing a card sets the outline on the map. Pressing a pin or an area selects it and scrolls its card into view. The focus is not taken to the card: it stays on the pin that was pressed, which takes it for itself, because the map takes a press for its own and left the focus on nothing. Nothing pans unless the selected area is off screen.
- **"Show in the list" opens the list at the top of the card.** A card is taller than a phone's screen. Brought to the nearest edge, it opened at its middle, 1,056 px past its heading. It is brought in by its top, and then given the focus.
- **The map can be skipped to.** The list comes before the map in the page and holds a hundred stops: by keyboard the map was 122 presses of Tab after the box. "Skip to the map" stands beside "Skip to results", and brings the map forward on a narrow screen, where it is behind a tab.
- **The equivalent list.** `AreaTable` holds every area of the release: rank, name linked to its page, borough, fit, and status in words, in rank order and then by name. It is always one tab away from the map and says everything the map does. An area with no rank says "Not ranked" and "No fit": it said "None", which reads as something the program left behind. The box the table scrolls in is positioned, so that the name kept for a screen reader in its last column is cut off with the rest: laid out against the page, it made the page 31 px wider than a phone and the whole page scrolled sideways.
- **Without WebGL** the map panel shows the table and one line saying why.
- **Tests.** `fillFor(scores, filtered, unranked)` and `buildStyle(theme)` are pure and tested. `maplibre-gl` is replaced in Jest by a stand-in that records calls. `buildStyle` is also held to MapLibre's own style specification, because no browser can say whether the style is valid. The map's style sheet is held against the library's, by the weight of their selectors: the library puts its own class on the map's element and sets `position: relative` on it, and where two rules weigh the same the one loaded last wins, which is the library's. With one class the map's element was no longer laid over its frame, had no height, and drew nothing. `test/support/css.ts` reads a style sheet as far as that needs.
- **Loaded on demand.** `src/lib/map/library.ts` imports the map library and its style sheet. `MapView` loads that file only once it knows the browser has WebGL and the boundaries are in hand, so a browser that cannot draw the map never fetches it.
- **Colours are read from the page.** `themeOfPage` reads the tokens of section 8 from the map's own element when the map starts, and again when the system turns dark or light. `style.ts` names the tokens and holds greys to fall back on.
- **The patterns are worked out, not drawn.** Each is an 8 by 8 tile of pixels made in code, in the colour of the outline, so no canvas and no image file is needed.
- **Nothing to rank by.** When `empty_spec` is true every area scores 0. The map then gives no area a band and no pin, and the list and the table show no fit.

## 10. Privacy in the browser

| What | May be held in | Never in |
|---|---|---|

| Place search text | The field, and the body of one `POST` to route 8 | The same |
| A `place_id`, a place name | The store. The body of a `POST`. The page, as text | A URL, storage, the console |
| The spec, `spec_hash` | The store. The body of a `POST` | A URL, storage, the console |

| Release id, engine version, `X-Request-Id` | Anywhere on the page | The console |

Rules the code keeps:

1. The website never touches `localStorage`, `sessionStorage`, IndexedDB, cookies, the Cache API or a service worker.
2. No analytics, no error reporter, and no script, style, font or image from another origin. A content security policy in `next.config.ts` allows the website's own origin and the API's, and no other. Next's own telemetry is switched off in every npm script.
3. The prompt form has `method="post"`, and the textarea and the search field have no `name`, `autocomplete="off"` and `spellcheck="false"`. If scripts fail, pressing Enter cannot put the text in a URL, and the browser does not keep it for next time. Nor does it check the spelling: a browser's fuller spell check sends the text of a checked field to its maker, which is a request to another party that no content security policy can stop.
4. The website calls no `console` method. The error boundary shows fixed text and reads nothing from the error.
5. Navigation goes only to paths built by `src/lib/paths.ts`, which takes a slug or nothing. `Referrer-Policy` is `no-referrer`, and a link to a source's site is `noreferrer`.
6. A link to an area, a source or a comparison is not fetched ahead of time, so the website's own server is not told what a person is reading before they ask for it.

Each test plants a canary, a string found nowhere else, in the prompt, in the place search and in a place name of a stand-in answer. It then runs a whole search. `test/privacy/search.test.tsx` reads, asks, ranks, refines, fails and goes offline. `test/privacy/share.test.tsx` searches, chooses areas, makes a link twice, copies it and opens the comparison. `test/share/page.test.tsx` opens a link, and what is not one.
