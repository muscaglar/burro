# Burro website: design

Status: design for the first build, 2026-09-23. The foundation of `apps/web` is built: the API types and client, the recorded answers, the tokens, the shell, and the methods, sources and accessibility pages. So is the search page, with its chips, its settings, its result cards and its map. So are the page of an area, the comparison, sharing, the sitemap and the robots file. The parts were then put together and gone over as one website: the answers were recorded again from the API as it then stood (engine 1.3.0; it moved three times while this was done, from 1.1.0, and the recordings followed it each time), every built page was read, one whole visit was walked against the service's own answers, and the website was answered with what it did not expect. What each of these settled is written in where it applies. It has since been run in a browser once, and read by two reviewers. The browser showed four things no test could: the map drew nothing, a button lay over the map, there was no icon, and a strength was given as a trade-off. The reviewers found nineteen more. What was put right is written in where it applies, each with the test that would have caught it. It was then walked through in a browser against the service itself, at the width of a phone and of a desk, by mouse and by keyboard. That found nineteen things more, of which the gravest was that a sentence could lose its budget and its workplace and the page ranked as if it had read them. What the website could put right is written in where it applies, and what needs the service is in section 13, gaps 17 to 22. Section 9 ends with the checks that must be made by hand, because no test can make them. The README says what to type to see the website in a browser. The search page was then rebuilt to [slice 1](slice-1.md), against contract version 2 and engine 1.4.0: the answer comes first, a vibe is shown as a band between two ends, a search can start from a shelf of words, and what the reader noticed and did not apply is offered and never guessed. Sections 1, 3, 4, 5, 6 and 7 say what that changed. Section 4.1 says what a results page holds before anything is opened, and what was measured of it in a browser. Section 13 says which gaps the contract has closed. The page of an area was then rebuilt to open with the portrait, and the comparison, the areas most like an area and a page of vibes were built with it. Sections 2, 4.2, 5.3, 7, 9, 10 and 12 say what that changed, and section 4.2 what was measured of it in a browser. The census figures of an area were then built on the made-up city, as the last of the parts of its page that are closed: section 2.1 gives the rules of how they are shown, and what was measured of them in a browser at both sizes.

This is the single source for the website in `apps/web`. It applies [PLAN](../PLAN.md) sections 4, 5, 8 and 9, ADRs [0002](../adr/0002-deterministic-core.md), [0005](../adr/0005-raw-prompts-are-never-stored.md), [0006](../adr/0006-rank-places-not-residents.md), [0008](../adr/0008-package-sources.md) and [0011](../adr/0011-nothing-is-kept-for-a-search.md), and [the contract](contract.md) sections 4, 5, 8 and 9. Where this document and the contract disagree, the contract is right and this document changes. Three people build three parts: section 11 says who owns what and where the parts meet. Section 13 lists what the contract does not yet give the website, and what the website does until it does.

## 0. Terms and the three rules

| Term | Meaning |
|---|---|
| Route N | The route with that number in contract section 9.2 |
| A type in `code` | The schema of that name in `contracts/openapi.json`, generated into `src/lib/api/schema.d.ts`. Never written by hand |
| API text | A string the API returned: a sentence's `text`, `notice_text`, an error's `message`, a fact's `label`, or a value in its `slots` |
| Site copy | Words kept in `src/content/`. They name controls, states and codes. They never hold a number or a proper noun about a place |
| The store | The one object in memory that holds a search (section 5.3) |

1. **Words about a place are API text.** The website lays API text out. It does not write, join or reword it. It formats no number that a fact's `slots` hold already formatted. It never prints a percentile: `slots.standing` says where a figure sits, and is literally true.
2. **The spec on screen is the last spec the API returned.** The website builds edits, never specs.
3. **What a person types stays in the box it was typed in, and in one `POST` body.** Section 10 lists everything else that is held, and where.

Wide screens, 60rem and over, put the map beside the list, where it stays while the list scrolls. Narrower ones put the first result directly after what Burro understood, whole on the first screen, and then the ways to the settings and to sharing, a strip of the map with the whole map one press away, and the rest of the results. There are no tabs: the list, the map and the way to the table are on one page at every width, so nothing is behind a tab when the answer comes.

- **The answer comes first, and on a phone the first result is whole on the first screen.** It was not: after a search the first screen of a phone held the banner, the header, the title, the box, a line of two, the chips, two buttons, a strip of map and two more buttons, and the first result began at 750 px and ended at 1,110 on a screen of 844. What stood above it was cut. Once a search is open the title takes no room, and is kept as the heading of the page for whoever hears it. On a narrow screen the banner is one line, "This is made-up test data.", and says all of it before a search and on every other page. What happened is one short line: "22 areas ranked. What you asked for counts most." Where a journey or a budget counts for more than anything that was asked of the place, the line says that in its place: "21 areas ranked. Journey and budget count most." A person who asked for leafy and quiet and named a workplace is first shown the areas nearest the workplace, and must not read the first result as the leafiest. It is said of every ranking it is true of, and the chips, once they are opened out, say where to change it (`src/lib/search/leads.ts`). The name of the first result is said to a screen reader and not drawn, because its card stands directly under the line. The heading "Results" takes no room. The settings, sharing and the map stand after the first result.
- **The list of results is drawn in two parts, with the map between them.** The first result is one list, and the rest another that says it begins at the second. It is one order of the page at every width: the form, the first result, the ways to the settings and to sharing, the map, the rest. On a wide screen the map is laid out beside them all. The map is the same map before a search and after one: nothing moves it, and it is not drawn again when the results come.

- **The banner** is site copy, shown on every page while `meta.synthetic` is true, at build or in any answer since: "This is made-up test data. The city, its places and every figure are invented. Nothing here describes a real place." It cannot be closed.
- **The preview banner** is site copy too, shown on every page built on a release whose `meta.preview` is true: "This is a preview for the people who build Burro. It is not finished: what it has not measured is missing, and nothing in it has been approved for the public." It cannot be closed. It says nothing of whether the figures are made up, so a preview of real data shows it alone and a made-up preview shows both. It is shown if the release the page was built on is a preview, and as soon as any answer says its release is one, by the body or by the header `X-Burro-Preview`. Then it stays. On a narrow screen, once a search is open, it is one line, "This is a preview.", as the banner of made-up data is: on a phone it was six lines, 138 px of a screen of 844, above the answer. Before a search, and on every other page, it says all of it.
- **A page is shown only while every answer is of the kind of data it was built on.** A page is built on one release and may be read while the service holds another. If an answer says its data is made up and the page was built on data that is not, or the other way, or one is a preview and the other is not, the page gives way to a notice: "This page cannot be shown. This page was built on one kind of data, and the service now answers with another: one of them is made up or unfinished, and the other is not. Nothing is shown, so that no figure is read under the wrong notice. The website must be built again on the release the service holds." So no real figure is read under "made-up", and no made-up figure as real. A release that moved on to another of the same kind changes nothing here: section 5 says what the search does then.
- **The line under the box** says two things. The first is the website's own: "What you type is sent to Burro to be read, and Burro does not keep it." The second is the service's: `reader.notice` of route 11, drawn as it was served, with a link to `reader.terms_url` where there is one. It says whose language model reads what is typed, what goes with it, that nothing private should be typed and that Burro itself keeps nothing of it, or that nothing typed is sent to a language model. What the company does with what it is sent is in the company's own terms, which the link leads to. The website writes no provider's name and no terms of its own, and a test reads its source for both (ADR 0019). The page is built ahead of time, so it asks the service as it opens and shows nothing of what it was built on in its place. Until the service has said, the line says that it is being asked, and no sentence is sent. Both are drawn in full before anything is sent. Once a search is open they give way to a link beside the label of the box, "How your words are handled", which leads to the same words on Methods.
- **A kind of house that was assumed is always named in the row of chips.** A chip folds two parts that nobody said into "rest assumed". Where Burro took a terraced house for "a house", the kind is named with the word "assumed" on it, whatever else was assumed: "£600,000, A terraced house assumed, flexible assumed". It is what the budget is held against, and nobody said it. After one press the website marks it from the edit that holds the kind, which says it is Burro's.
- **The examples** hold no proper noun, so none can go stale when a release changes. They are for a first search. Once a search is open they go, because an example pressed then would be added to it: "Buying a terraced house" on top of "leafy and quiet". They come back with "Start again".
- **What Burro says of a search stands directly under the box.** In a browser, pressing Search changed nothing on screen: on a phone what was understood began a screen and a half down, under the examples, the tenure and the place field. Now nothing stands between the box and what Burro says. Section 4.1 gives where each part was measured to stand. Before a search the page is the box, the shelf, the tenure and the place field, the examples, and the way to the settings. It holds no chips: nothing has been understood of anything.
- **Once a search is open the box says that what is typed is added to it**: its label reads "Add to this search", and "Start again" stands beside Search. It empties the box, puts the focus in it, and goes back to the page as it first stood, with the defaults the API served. Nothing of the search before is left: the tray of areas to compare is emptied, and no area is chosen on the map.
- **What goes when a search opens hands the focus on.** A word of the shelf that is added, and a place picked from the field, open the search, and the shelf and the field go with it. The focus goes to what Burro understood, and is never left on nothing.

## 2. Pages and routes

One environment variable says where the API is: `NEXT_PUBLIC_BURRO_API_URL`. The browser calls that address itself. The website has no route handler, no server action and no middleware, so nothing a person types passes through the website's server. The server calls the same address only while it builds a page, and only routes 4, 5, 6 and 11. With the variable unset a build reads the recorded responses of section 11, which is how a build runs where no API can, and the browser's client answers `not_configured` without sending anything. `src/lib/api/config.ts` reads the variable, `next.config.ts` reads it for the content security policy, and a test fails if any other file does. A second variable, `BURRO_SITE_URL`, says where the website itself is. It is read on the server, in `src/lib/indexing.ts` and nowhere else, and is used for what a search engine is told and for nothing else.

- `[city]` is `synthetic` for ids that begin `syn` and `london` for `lon`. `src/lib/city.ts` holds the pair and nothing else does.
- **One rule says whether anything may be indexed**, and it is in `src/lib/indexing.ts`: a page may be indexed only when the release is real, is no preview, and the website knows its own address. The address comes from `BURRO_SITE_URL`, read on the server and in that one file. While the rule says no, every page carries `noindex, nofollow`, every answer carries the header `X-Robots-Tag: noindex, nofollow`, the robots file names no sitemap, the sitemap lists nothing, and an area's page has no canonical address and no structured data. **The robots file never keeps a crawler out.** One that is kept out never fetches a page, so it never reads that the page asks to be left out, and may still list the address of a made-up place from a link it found elsewhere. The header says the same for what is not a page and can carry no `robots` of its own, such as the robots file and the icon. It is worked out when the website is built, from the same rule, and a release that cannot be read then is taken for one that may not be indexed. When it says yes, every page may be read, the sitemap lists the search, the three pages about the website and one page for each area from route 4, and an area's page carries its canonical address and its structured data. A comparison and the page a share opens are one person's: they carry `noindex`, in the page and in the header, whatever the rule says, and the sitemap never lists them. A test asks all of these at once and fails if any two disagree.
- **What an area's page tells a search engine is what its `area` fact says**, and no more. The title is the name and the borough. The description names them and then describes the page, not the place. The structured data is a `Place` with its name, its address on the website, and the borough as the place that holds it. It holds no figure and no coordinates: no fact holds where an area is. It is written into the page as the text of a script, with every `<` written as its escape.
- "Hourly" is a revalidation of 3,600 seconds: a built page is built again each hour. The API tells a browser to ask each time whether an answer of routes 4, 5, 6 and 11 still stands (`Cache-Control: no-cache`, with the release in the `ETag`), so a browser no longer answers one from its own cache for an hour (section 13, gap 15, met). If an answer in the browser names a `release_id` other than the one the page was built on, the browser fetches routes 4, 5 and 11 again and uses those. It does so beside the search and never in its way: reading the form again changes the form and the names of the areas, and takes nothing from the cards. It is asked for once at a time. If it cannot be read, or the boundaries cannot, the next answer that names the release asks again.
- A share is made in `SharePanel`, which opens in place beside the settings once there is a ranking. It says what the link will hold, offers "Share the exact places" unticked, sends route 9 with the spec the store holds, and shows the link `/s#share_id` in a field to copy from, with the stored spec as chips. If `coarsened` is true it says the ranking may differ a little. If nothing was replaced and the box was left unticked, it says that no place needed replacing, because each is a station or a district already: it said "The link holds the places as you named them", which read as if the choice had been ignored. A link is shown only for the search it was made of: change the search, and the link goes. The session keeps the link that was last made, so that it is still there when the person comes back from the page of an area.

What building the area page, the comparison and sharing settled:

- **The session.** The search that is open and the areas chosen to compare are held by `SessionProvider`, which the shell of every page holds. The shell stays while one page gives way to the next, so both are still there after a link inside the website is followed. Loading a page afresh, or closing the tab, loses both. Nothing is written anywhere: section 10 stands.
- **The areas to compare are not part of the search.** They are chosen from an area's page as well as from a result, and an area's page holds no search. The session holds them as each area's id, slug and name. "Start again" empties them: in a browser the tray still held three areas of the search before, under a page that otherwise stood as it first did.
- **The address of a comparison decides what is compared.** The tray builds the address, and the page puts the areas of its address in the tray, so going back to choose others starts from what was compared.
- **A comparison shows a fact's slots and never a cell's numbers.** A cell of route 7 holds `value`, `percentile`, `utility` and `contribution` as numbers. The page shows the slots of the fact the cell cites, as the API formatted them, and the contribution as "Adds 23 of 100 to the fit", rounded down. It never shows `value`, which is the same figure unformatted, nor `percentile`, nor `utility`.
- **Where an area stands is shown only from a search.** Route 7 gives no score. When a search is open and its ranking is of the spec that is sent, each ranked area shows its rank and its fit from that ranking. With no search open it shows neither.
- **The table is stacked on a narrow screen.** Under 60rem each row becomes a block: the thing that counts, then each area under its own name. It is one table in the page either way, and every row and cell says its role, so that a browser which forgets a table when it is laid out as blocks is told again.
- **An area's page gives the source under each fact, not behind a button.** `SourceLine` writes out what `SourceNote` opens, because the page must read with scripts off. Under what the area is like in short they are written out too, and are one press away: five lines of a build of a real city rest on thirteen sources and seven dates, which stood a screen and a quarter of a phone high between what the area is like and where it is. What opens them is the browser's own `details`, so they open with scripts off. Under a vibe the line begins with the API's own words, "Burro's recipe. Made from data published by:", from the slot `made_from`: the sources of a vibe are those of its parts.
- **The portrait opens with what the area is like, in five lines.** A person who has never been to the city opened the page of an area and read "band 4 of 5" eleven times. Under the heading "In short" the portrait now says what sets the area apart from the others of the release: what it has most of, where it sits between two ends, and what it has least of. Each line is one vibe the API placed: its name, where the area sits on it in words a person would use, and a figure of one of its parts. The vibes furthest from the middle band are chosen first, a kind at a time, so that what an area has least of is never crowded out by what it has most of (`inShort` in `src/lib/area/portrait.ts`). A vibe in the middle band is in no line of it, nor is a mixed area, which sits at no one point. ### 5.3 How typing and controls stay in step

One store holds the search. It is a React context over a plain object, with no library. `state.ts` holds the object and the one pure function that moves it on. `store.ts` holds it in memory and hands it to the page. `flow.ts` holds what a person can do, as the calls each makes. The session keeps the store while the tab is open (section 2), so a page that is not the search page reads the search with `useOpenSearch`. Beside the fields below, the store holds `pending` (edits not yet answered), `refused` (edits a control sent that the reducer rejected), `answers` (a count of the answers that leave no edit waiting, against which a control holds what it was set to), `untouched` (true until an answer changes the spec), `kept` (the search as it was when the sentence being read was sent, for Stop to put back), `settingsOpen` and `settingsByPage` (true while the settings are open because the page opened them and the person has not used them), `tenurePicked`, `quoted` (the word a vibe was read from, by chip, where the reader took a word one way of two), `budgetWent`, `rankedBefore` (how many areas the ranking before this one ranked), and what could not be loaded, each with the failure that says why.

`answers` does not move when a reading comes while an edit waits. The edit has not been answered, so the control that was moved keeps showing what it was set to until the ranking comes. A control nobody has touched is drawn from the spec whenever the spec changes.

- **Without WebGL** the map panel shows one line saying why, and the way to the table.
- **Tests.** `fillFor(scores, filtered, unranked)`, `fillForVibe(marks)` and `buildStyle(theme)` are pure and tested. `maplibre-gl` is replaced in Jest by a stand-in that records calls. `buildStyle` is also held to MapLibre's own style specification, because no browser can say whether the style is valid. The map's style sheet is held against the library's, by the weight of their selectors: the library puts its own class on the map's element and sets `position: relative` on it, and where two rules weigh the same the one loaded last wins, which is the library's. With one class the map's element was no longer laid over its frame, had no height, and drew nothing. `test/support/css.ts` reads a style sheet as far as that needs.
- **Loaded on demand.** `src/lib/map/library.ts` imports the map library and its style sheet. `MapView` loads that file only once it knows the browser has WebGL and the boundaries are in hand, so a browser that cannot draw the map never fetches it.
- **Colours are read from the page.** `themeOfPage` reads the tokens of section 8 from the map's own element when the map starts, and again when the system turns dark or light. `style.ts` names the tokens and holds greys to fall back on.
- **The patterns are worked out, not drawn.** Each is an 8 by 8 tile of pixels made in code, in the colour of the outline, so no canvas and no image file is needed.
- **Nothing to rank by.** When `empty_spec` is true every area scores 0. The map then gives no area a band and no pin, and the list and the table show no fit.

Rules the code keeps:

1. The website never touches `localStorage`, `sessionStorage`, IndexedDB, cookies, the Cache API or a service worker.
2. No analytics, no error reporter, and no script, style, font or image from another origin. A content security policy in `next.config.ts` allows the website's own origin and the API's, and no other. Next's own telemetry is switched off in every npm script.
3. The prompt form has `method="post"`, and the textarea and the search field have no `name`, `autocomplete="off"` and `spellcheck="false"`. If scripts fail, pressing Enter cannot put the text in a URL, and the browser does not keep it for next time. Nor does it check the spelling: a browser's fuller spell check sends the text of a checked field to its maker, which is a request to another party that no content security policy can stop.
4. The website calls no `console` method. The error boundary shows fixed text and reads nothing from the error.
5. Navigation goes only to paths built by `src/lib/paths.ts`, which takes a slug or nothing. `Referrer-Policy` is `no-referrer`, and a link to a source's site is `noreferrer`.
6. A link to an area, a source or a comparison is not fetched ahead of time, so the website's own server is not told what a person is reading before they ask for it.

Each test plants a canary, a string found nowhere else, in the prompt, in the place search and in a place name of a stand-in answer. It then runs a whole search. `test/privacy/search.test.tsx` reads, asks, ranks, refines, fails, goes offline, and sends a sentence that is not plain, of which it chooses one thing and leaves one out. `test/privacy/share.test.tsx` searches, chooses areas, makes a link twice, copies it and opens the comparison. `test/share/page.test.tsx` opens a link, and what is not one.
