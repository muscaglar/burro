# llm-architecture: LLM architecture on the Anthropic Claude API (query understanding, grounded explanation, refinement, vibe matching, offline profiles, evaluation, safety, cost, streaming)

## Headline
Keep the LLM at the edges of a deterministic core. Use Claude Haiku 4.5 with structured outputs to turn language into a versioned PreferenceSpec and into typed spec-edit operations; rank with a pure deterministic engine; write explanations with the Citations API over a per-area fact pack and verify every block server-side before it is streamed. Score a fixed vocabulary of vibe tags offline with Claude Opus 5.5 through the Batch API, with human review; defer embeddings and pgvector. Budget about USD 18 per 1,000 searches (USD 23 with contingency), with a hard floor of about USD 2 when explanations fall back to deterministic reason chips.

## Summary
WHAT I CHECKED TODAY (2026-09-23, public Anthropic docs). Current line-up: Claude Fable 5.1 (claude-fable-5-1, $10/$50 per MTok), Claude Opus 5.5 (claude-opus-5-5, $4/$20, docs' recommended default), Claude Sonnet 5 (claude-sonnet-5, $2/$10), Claude Haiku 4.5 (claude-haiku-4-5, $1/$5). Batch API is 50% off. Cache reads are 0.1x input (0.05x on Opus 5.5, 0.025x on Fable 5.1); cache writes 1.25x (5 min) or 2x (1 hour). Structured outputs and Citations are both GA on all four models, but cannot be combined in one request (400 error). Anthropic has no embeddings endpoint and points to Voyage AI.

ARCHITECTURE
(a) Interpret: one Haiku 4.5 call with a JSON-schema-constrained output returns status (ok / clarify / off_topic / policy_redirect), a PreferenceSpec, stated assumptions, unmet requests and policy flags. Destinations are returned as strings and resolved by a deterministic gazetteer, never by the model. Ask a clarifying question only when a hard constraint is unusable (no tenure and no budget, a destination that cannot be resolved, or contradictory hard constraints). Otherwise proceed and show assumptions as editable chips.
(b) Ranking: pure function of (spec, data snapshot, engine version). Hard filters eliminate, soft weights multiply percentile-normalised utilities, commute uses a piecewise decay over precomputed travel times, combined across destinations by worst-case or weighted sum. It returns per-feature contributions, which drive the on-screen breakdown.
(c) Explanations: each fact is one content block in a custom-content document per area. Citations return block indices that map to fact IDs, with guaranteed valid pointers. The server buffers per block, drops uncited blocks that contain numerals or place names, checks numerals against the cited fact, and falls back to template text on failure. Raw user text is never passed to this call.
(d) Refinement: the model emits typed operations (adjust_weight, set_budget, add_commute, exclude_area and so on), not a new spec. Sliders emit the same operations without an LLM call. One reducer, immutable spec versions, undo for free.
(e) Vibe: fixed tag vocabulary of 40 to 60 tags scored offline per area, mostly from data, with LLM scoring from open text as a secondary input. No embeddings in v1.
(f) Profiles: Opus 5.5 via Batch, stored as reviewed files in the repo, regenerated on data snapshot change.
(g) Evaluation: three tiers, from free deterministic tests on every PR to a live golden set and an LLM judge nightly.
(h) Safety: schema-constrained outputs, no protected-characteristic features, amenity-based handling of affinity requests, a disparate-impact audit.
(i) and (j): cost, limits and streaming below.

COST PER 1,000 SEARCHES (token counts are my estimates, to be measured with count_tokens)
Definition of one search: 1 interpret + 1.5 chat refinements + 2 explanation calls for the top 5. Slider edits cost nothing.

THE MAIN THINGS TO DECIDE
1. Whether demographics belong in the vibe signal at all. I recommend excluding every protected characteristic, including age structure, from ranking features and using amenity-based proxies.
2. Whether user-facing explanations justify Sonnet 5 at roughly +$14 per 1,000 searches. I recommend starting on Haiku 4.5 and making richer explanations a premium entitlement, decided by eval rather than by assumption.
3. Legal review of the Equality Act position and of share-alike obligations for Wikipedia-derived content before launch.

## Recommendations
- **Model for online interpret and refine calls** [medium]: Claude Haiku 4.5 (claude-haiku-4-5), thinking off, structured outputs via client.messages.parse() with a Pydantic model, max_tokens about 1,024
  - why: This call blocks the first results, so latency dominates. It is an extraction and classification task, which the public model-selection guide places with Haiku. Structured outputs guarantee schema-valid JSON, so the failure mode is a wrong value, not a broken parse, and the golden set measures that directly. Keep the model ID in config so it can be swapped after an eval run.
  - rejected: Sonnet 5 for every structured call: about $40 per 1,000 searches versus $18, and slower on the critical path. Keep it as the tested fallback. Opus 5.5 online: about $104 per 1,000, thinking cannot be disabled, and forced tool_choice returns 400. Fable 5.1: priced for long-horizon agent work and requires 30-day data retention.
- **Model for online explanations** [medium]: Claude Haiku 4.5 with Citations for the free tier at launch; run the same eval on Sonnet 5 (thinking disabled) and offer it as the premium-tier explanation model if the judge and a human read show a clear gain
  - why: Explanations are short (about 70 tokens per area) and fully grounded in a supplied fact pack, so world knowledge matters little. Streaming hides latency. Output tokens dominate cost, so the model choice is a direct cost lever and a natural entitlement.
  - rejected: Template-only explanations: zero risk and zero cost, but they read as mechanical. Keep them as the fallback and as the always-present reason chips. One call per area in parallel: independent failure and caching, but repeats the uncached system prompt five times on Haiku.
- **Model for offline profile and vibe-tag generation** [medium]: Claude Opus 5.5 (claude-opus-5-5) through the Message Batches API, with 1-hour cache TTL on the shared prefix
  - why: A full run over about 500 areas costs roughly $27, so there is no reason to economise on quality. Batch gives 50% off and most batches finish within an hour. Opus 5.5 is the public docs' recommended default and was released this week, so pin it and keep Opus 5 (claude-opus-5) as the conservative alternative if early behaviour disappoints.
  - rejected: Haiku 4.5 offline: saves under $25 per run and lowers quality on the one artefact humans will read closely. Fable 5.1: about 2.5x the cost for a task that does not need long-horizon reasoning.
- **PreferenceSpec design** [high]: A versioned, flat schema: tenure, budget (amount, period, bedrooms, strictness), commute list (raw_text, resolved destination_id, modes, max_minutes, strictness, time band, weight), commute_combine, hard_filters from a whitelist, weights as an array of {feature, weight, provenance}, vibe tags as an array of {tag, weight}, area include and exclude lists, assumptions, unmet_requests, policy_flags
  - why: Structured outputs do not support recursive schemas, numeric minimum or maximum, or additionalProperties true. Arrays of enum-keyed items keep output short, which cuts latency. The SDK strips unsupported constraints before sending and re-validates the response against the original Pydantic model, so range checks still run. Provenance per field (user_stated, inferred, default, ui_edit) lets the interface show what was assumed.
  - rejected: Free-form JSON with prompt instructions only: no validity guarantee. A fixed object with 35 required weight keys: longer output and slower. Tool use with strict:true instead of output_config.format: equivalent guarantee, but forced tool_choice is rejected on Opus 5.5 and Fable 5.1, which would block a later model swap.
- **When to ask a clarifying question** [medium]: Ask only when ranking would be meaningless: tenure and budget both missing, a commute destination that the gazetteer cannot resolve or resolves ambiguously, or contradictory hard constraints. At most one question, with tappable options. In every other case proceed with stated assumptions shown as editable chips
  - why: Relocating users cannot answer questions about London geography, and every question is a drop-off point. Ambiguous destinations are better resolved by a deterministic disambiguation list than by the model. Results plus visible assumptions teach the user what to refine.
  - rejected: An interview-style multi-question flow before results: slower and more LLM calls. Never asking: produces confident nonsense when the budget or tenure is unknown.
- **How the ranking engine consumes the spec** [high]: A pure function rank(spec, data_snapshot_id, engine_version) returning ordered areas with per-feature contributions. Canonicalise the spec (sorted keys, weights rounded to 0.05) and hash it for caching and shareable links. Hard filters first, then weighted sum of percentile-normalised utilities, stable tie-break on area ID
  - why: Determinism makes results reproducible for shared links, testable without an LLM, and explainable: the contribution table is the explanation's source of truth. With a few hundred areas the computation takes milliseconds, so sliders can re-rank without any model call.
  - rejected: Letting the LLM rank or re-rank candidates: not reproducible, not explainable, and open to manipulation through the prompt. A learned ranking model: no training data exists before launch.
- **Grounding mechanism for explanations** [medium]: Citations API with one custom-content document per area, one fact per content block, plus a server-side verifier that runs per block before anything is sent to the client
  - why: The API guarantees that citations point at supplied blocks, cited_text is not billed as output, and responses stream as separate text blocks, which makes per-block verification natural. Custom content gives exact control of granularity, so a block index maps one-to-one to a stored fact ID with its source and date.
  - rejected: Structured output with fact_id arrays: guarantees valid IDs but not that the sentence matches the fact, and cannot be combined with citations. Placeholder substitution, where the model writes {fact_id} tokens and the server inserts values: the strongest guarantee on numbers and my recommended fallback if evals show numeric drift, but it needs a custom protocol and stiffer prose.
- **Conversational refinement and slider sync** [high]: The model returns a list of typed operations plus a reply of at most 200 characters. Relative requests map to bounded steps (up_small, up_large, down_small, down_large). Slider and filter edits emit the same operations client-side. The server applies operations through one reducer, stores an immutable spec version with a parent pointer, re-ranks, and sends the new spec and the diff to the client
  - why: A single operation vocabulary is what keeps chat and controls in step in both directions. Diffs are small to generate, easy to show to the user, easy to undo, and easy to assert on in tests. Feeding the model a compact log of recent operations, including slider moves, keeps the conversation aware of manual edits without resending a transcript.
  - rejected: Regenerating the full spec on each turn: silently drops earlier preferences and produces unexplained changes. Generic RFC 6902 JSON Patch with free paths and values: harder to constrain in a strict schema and lets the model write to fields it should not touch.
- **Semantic vibe matching** [high]: Offline-scored vibe tags as the only ranking signal for vibe in v1. 'Areas like X' uses nearest neighbours on the standardised feature and tag vector. Add embeddings only if more than about 10% of real queries contain vibe phrases that map to no tag
  - why: Tags are explainable, reviewable, deterministic and auditable for bias. The full tag vocabulary fits in the cached prompt (about 1,500 tokens), so the interpret call already maps open language to tags better than a nearest-neighbour lookup would. Text-embedding similarity cannot be explained to a user and can carry demographic proxies from source text into the ranking.
  - rejected: Embeddings as the primary signal: opaque scores, extra vendor, and text-quality bias between well-documented and poorly-documented areas. pgvector in v1: unnecessary below roughly 10,000 rows, where exact search in memory is instant.
- **If embeddings are added later** [medium]: Embed documents offline with voyage-4-large through the API and embed queries locally with the open-weight voyage-4-nano (Apache 2.0), stored as 1,024-dimension vectors in pgvector with exact search
  - why: Voyage states the four Voyage 4 models share one embedding space, so documents and queries can use different models. That gives the best document quality with no per-query vendor call and no user text leaving the server. The first 200M tokens are free, which covers the whole corpus many times over.
  - rejected: Qwen3-Embedding-0.6B or BGE-M3 self-hosted: permissively licensed and capable, but no matching hosted large model for the offline side. Sending user queries to the Voyage API: by default Voyage takes a licence to train on customer content unless an admin opts out, and opting out may void free tokens.
- **Offline profile generation and review** [medium]: Per area, build an evidence pack of stored facts plus open-text excerpts. Run two batch calls: tag scores with evidence and confidence (structured output), and profile prose (citations). Run automated checks, then human review of every profile before first launch and of diffs only afterwards. Store as files in the repo with generation metadata
  - why: Files in the repo give diffable review through pull requests, which suits both people and coding agents. A one-off review of 300 to 600 short profiles is roughly 15 to 30 hours, which is proportionate for published text about real places. Writing prose from structured facts only, and using open text solely as tag evidence, limits share-alike exposure.
  - rejected: Generating profiles on demand at request time: slower, costlier, unreviewed, and non-deterministic. Spot-check review only at launch: too risky for text that characterises neighbourhoods. A custom review web app: more to build than the review is worth in v1.
- **Evaluation and CI** [high]: Tier 1 on every PR with no LLM calls: ranking property tests, reducer tests, verifier tests, replayed recorded responses. Tier 2 on PRs touching prompts, schemas or model config, and nightly: live golden set of 150 to 250 queries with code-graded field assertions. Tier 3 nightly: ranking expectations curated by a Londoner, and Sonnet 5 as judge of explanation quality with binary rubric items. Plain pytest and a thin in-repo runner
  - why: Most of the system is deterministic and can be tested for free. Field-level assertions are more robust than whole-spec equality. Anthropic's guidance is to use a different model to judge than to generate, to prefer code grading where possible, and to favour volume. A full live run costs about $3.40, so nightly runs are affordable. The same golden set is the gate for any model change.
  - rejected: A third-party eval framework: extra dependency and concepts for a small team. Judge-only evaluation: judges can be gamed and fixate on surface features. Whole-spec exact match: brittle against harmless variation.
- **Checks for invented facts** [high]: Online, on every response: every numeral and every place, station or line name in an explanation block must appear in the cited facts or the spec; failures are replaced with template text and logged. Offline: missing-data tests (remove rent from the pack, the text must not mention rent) and perturbation tests (change a value, the text must change with it)
  - why: Perturbation tests prove the model is reading the pack and not recalling from training, which matters because Haiku 4.5's reliable knowledge cutoff is February 2025. Running the verifier before the block is sent means an invented figure never reaches a user.
  - rejected: Relying on the prompt instruction alone: Anthropic's own guidance says these techniques reduce but do not eliminate hallucination. Verifying only in evals: leaves production unprotected.
- **Prompt injection and off-topic abuse** [high]: No general chat surface. Interpret and refine outputs are schema-constrained with enums and short bounded strings. The explanation call receives the normalised spec and canonical gazetteer names, never raw user text. Third-party text is used only offline and human-reviewed. Input capped at about 600 characters, max_tokens capped, per-device and per-account quotas, bot challenge on web, a daily spend circuit breaker that degrades to deterministic-only mode, and an Anthropic workspace spend limit as a backstop
  - why: The safest defence is to make a successful injection useless: there are no tools with side effects and no free-text channel that user input can steer. An off-topic request costs one interpret call, about $0.002. Without a circuit breaker, a bot using 10,000 addresses at three searches a day would cost about $540 a day.
  - rejected: A separate screening call before every interpret call: doubles latency for little gain when the interpret call already classifies and cannot act. Hard failure when the spend cap is hit: a form-based deterministic mode keeps the product usable.
- **Discriminatory requests and Equality Act 2010 exposure** [medium]: Exclude all nine protected characteristics, and close demographic proxies for them, from ranking features, tags and profile text. Describe places and amenities, never residents. Serve positive amenity requests (a mosque nearby, kosher shops, step-free stations) through points-of-interest and accessibility features. Decline requests to avoid or minimise a group in one neutral sentence and continue with the rest of the query. Do not store protected characteristics a user volunteers. Run a periodic offline audit of ranking outputs against census composition
  - why: Burro is a service-provider under section 29, and section 13(5) treats racial segregation as less favourable treatment. Ranking by who lives somewhere is the conduct that steering rules target. Anthropic's Usage Policy separately prohibits promoting discriminatory practices. Amenity requests treat every user identically and rank on facilities, which is a defensible line. The audit addresses indirect discrimination under section 19, where a neutral-looking feature acts as a proxy. This is a design position, not legal advice.
  - rejected: Blocking the whole search on any flagged phrase: punishes clumsy wording and loses the legitimate parts of the query. Offering composition data 'for information': creates the steering risk directly. Using age-structure data for 'young professional' or 'family' vibes: age is a protected characteristic, so use amenities such as nurseries, schools and late-opening venues.
- **Prompt caching** [high]: One stable system prefix of at least 4,096 tokens for interpret and refine (instructions, feature dictionary, tag vocabulary, policy rules, worked examples). Use 1-hour TTL with a keep-warm request at low traffic, 5-minute TTL once traffic exceeds one request every few minutes. Assert cache_read_input_tokens is non-zero in a smoke test
  - why: Haiku 4.5 silently skips caching below 4,096 tokens, so the prefix must be sized deliberately. A warm cache cuts the interpret call from $0.0066 to $0.0021. Citations and output format changes each invalidate the system cache, so interpret and explain need separate prefixes. Cached reads do not count toward input-token rate limits.
  - rejected: Sharing one prefix across interpret and explain: not possible because toggling citations and output format invalidates it. Putting timestamps or request IDs in the system prompt: breaks the prefix on every call.
- **Application-level caching** [high]: Cache normalised query text to spec for 24 hours, spec hash plus data snapshot to ranking, and area plus spec signature to explanation. Precompute landing-page example queries. Warm the structured-output grammar on deploy
  - why: Example and shared queries repeat exactly, so they should cost nothing. Compiled grammars are cached for 24 hours from last use and the first request after a schema change is slower, so a deploy-time warm-up keeps that off the user's path.
  - rejected: Semantic (embedding-based) query cache: adds a dependency and risks returning a spec for a subtly different request.
- **Rate limits and entitlements** [medium]: Limits as configuration keyed by plan. Proposed starting values: anonymous 3 searches a day and 5 chat refinements per search; free account 15 a day and 10 refinements; premium 100 a day, 30 refinements, Sonnet 5 explanations and comparison narratives. Slider edits unlimited on every plan
  - why: Every LLM-costing action passes through one entitlement check, so a paid tier needs a new row of limits and not new code. Unlimited sliders cost nothing and keep the free product generous. Anthropic Start-tier limits for Haiku 4.5 (1,000 requests, 2M uncached input tokens and 400k output tokens per minute) support roughly 200 searches a minute, far above launch needs.
  - rejected: Hard-coding limits in handlers: forces a rewrite when premium launches. Token-based user quotas: hard for users to understand.
- **Streaming to web and iOS** [high]: Server-sent events from FastAPI's native fastapi.sse, with Burro's own event schema: status, spec, clarify, results, explanation.delta, explanation.done, error, done. The server consumes Anthropic's stream, verifies per block, and re-emits. Every search also has a plain GET snapshot endpoint. Web reads the stream with fetch and a stream reader; iOS uses URLSession async bytes
  - why: The flow is one-directional, so SSE is sufficient and simpler than WebSockets through proxies. Re-emitting keeps the API key server-side, allows verification before display, and insulates clients from Anthropic API changes. The snapshot endpoint makes reconnects, app backgrounding and shared links trivial, because the stream is an enhancement and not the source of truth.
  - rejected: Proxying Anthropic's raw event stream to clients: exposes unverified text and couples both clients to a vendor format. Browser EventSource: GET only and no custom headers. WebSockets: more moving parts for no benefit here.
- **Consumer disclosure** [high]: State at the start of each session, on web and iOS, that interpretation and explanations are AI-generated, and show the source and date behind every cited fact
  - why: Anthropic's Usage Policy requires consumer-facing interactive AI products to disclose that users are interacting with AI. Source-and-date display also supports the explainability promise.
  - rejected: Disclosure only in terms of service: does not meet the policy's per-session wording.

## Risks
- [high] Ranking or describing areas by who lives there exposes Burro to discrimination claims under the Equality Act 2010 and breaches Anthropic's Usage Policy. The brief currently lists demographics as a vibe input. -> Remove all protected characteristics and close proxies from features, tags and text. Use amenity-based signals. Classify and decline avoid-a-group requests while serving the rest of the query. Run a periodic offline audit of outputs against census composition. Obtain legal advice before launch.
- [high] An explanation states a figure or fact that is not in stored data, which undermines the product's central promise. -> Citations over per-fact blocks, per-block verification before display, template fallback, perturbation and missing-data tests in CI, and logged verifier failure rates. Switch to placeholder substitution if numeric drift exceeds a set threshold.
- [high] Automated abuse of a free endpoint runs up LLM cost. Ten thousand addresses at three searches a day is about $540 a day. -> Bot challenge on web, device attestation on iOS, anonymous quotas, sign-in after a few searches, a daily spend circuit breaker that degrades to deterministic-only mode, and an Anthropic workspace spend limit.
- [medium] Haiku 4.5 is the oldest model in the line-up, with retirement 'not sooner than 15 October 2026'. It is still Active and no deprecation has been announced, but a successor or deprecation notice is plausible during the build. -> Model IDs in configuration. Golden set as the migration gate. Sonnet 5 with thinking disabled tested as a drop-in from day one, at about 2.2x the cost. Anthropic commits to at least 60 days' notice.
- [medium] My token counts are estimates. Schema injection, citations overhead and the newer tokenizer on Sonnet 5 and Opus 5.5 could raise real cost by 30% or more. -> Measure with the token counting endpoint in the first week. Log usage fields from every response. The $23 figure already includes 25% contingency.
- [medium] Prompt caching silently fails because the prefix is under 4,096 tokens on Haiku 4.5 or because something volatile enters the prefix. Interpret cost roughly triples. -> Size the prefix deliberately above the threshold with useful worked examples. Add a smoke test asserting cache_read_input_tokens is non-zero on the second call. Keep timestamps and IDs out of the system prompt.
- [medium] Interpret latency on the critical path is slower than the 2 to 3 second target, since Anthropic publishes no throughput figures and my estimate is unverified. -> Keep output compact (only non-default fields, enum values, no prose). Put status and destinations first in the schema so geocoding can start early. Show interpreted chips as they arrive. Measure p50 and p95 in a spike before committing to the interaction design.
- [medium] Profiles or tags derived from CC BY-SA text may carry share-alike obligations onto Burro's published content. -> Write prose from structured facts only. Use open text only as tag evidence, with attribution. Never reproduce or closely paraphrase it. Take legal advice on whether derived tag scores are adaptations.
- [medium] LLM-scored vibe tags encode stereotypes or uneven source coverage, so well-documented central areas score richer than outer ones. -> Derive tags mainly from data with documented formulas. Store evidence and confidence per score. Flag low-evidence areas. Human review all tags before launch. Generate twice and flag disagreement above 0.2.
- [medium] No UK or EU inference geography exists on the first-party API, and user queries may contain personal details such as workplaces. -> Cover international transfer in the privacy notice and data processing agreement. Minimise what is sent: no account identifiers, no stored protected characteristics. Consider whether saved workplace locations need separate handling.
- [low] The LLM judge drifts from human judgement or rewards surface features, giving false confidence. -> Binary, checkable rubric items. Calibrate against about 50 human-labelled examples and track agreement. Feed the judge empty and wrong-but-confident outputs and confirm it fails them. Prefer code-graded checks wherever possible.
- [low] A shared link shows different results later because data or the engine changed. -> Store the data snapshot and engine version with each result. On open, show the original ranking with a notice and an option to refresh.
- [low] Opus 5.5 was released this week, so offline generation may hit early behaviour changes or undocumented quirks. -> Offline only, human-reviewed, and inexpensive to rerun. Keep claude-opus-5 as the alternative.


## Open questions
- Should any demographic data feed the vibe signal? I recommend none that touches a protected characteristic, including age structure. This changes the brief's stated vibe inputs and needs the founder's decision.
- How should Burro respond to positive affinity requests such as 'a strong Jewish community' or 'LGBTQ+ friendly'? I propose ranking only on amenities and venues, never on population composition. Is that acceptable to the founder and to a solicitor?
- Is deprivation or income data acceptable as a ranking feature? It is not a protected characteristic, but it correlates with race and could support an indirect discrimination argument.
- Will Burro ever pass leads to estate agents or landlords? That would bring the Usage Policy's high-risk housing provisions and Equality Act section 111 into scope.
- Are profile text or tag scores informed by Wikipedia or Wikivoyage 'adaptations' under CC BY-SA 4.0? This needs legal advice.
- How many neighbourhoods will v1 contain, and how many facts per area? Both drive the explanation call's input size and the offline cost.
- Who reviews profiles and tags before launch, and is 15 to 30 hours of review time available?
- What daily LLM spend cap is acceptable at launch, and should the product degrade to deterministic-only mode or queue users when it is reached?
- Is Sonnet-quality explanation text worth about $14 more per 1,000 searches on the free tier, or should it be premium only? I would decide this from a side-by-side eval.
- Which gazetteer resolves commute destinations, and what are its licence terms? This sits with the data-sources workstream, but the interpret call's output format depends on it.
- What should happen to the raw query text after interpretation? Storing it helps evaluation but it may contain personal data such as a workplace or a health need.
- Does the founder want non-English queries supported at launch? The models handle them, but the golden set and the policy classifier would need multilingual cases.
