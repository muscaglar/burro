# verify:routing-feasibility - travel-time feasibility

The overall direction holds: an offline R5 precompute served as an array lookup is feasible, legal and cheap. Licences, versions and vendor terms mostly check out against primary sources. Four things need to change in the plan.

1. COMPUTE ESTIMATE IS NOT SAFE AS WRITTEN (major). The cited benchmark is real but is for r5r, which parallelises over origins in Java. I read the r5py source: since v1.0 TravelTimeMatrix loops over origins one at a time in Python, and R5's per-origin computation has no internal thread pool. On r5py as shipped, a 32-vCPU VM is no faster than one core. "1 to 4 hours" is achievable only with a custom parallel driver (several worker processes, each with its own JVM and network in memory) or a smaller origin set. Cost stays small either way; this is an engineering item, not a budget item.

2. BODS CONTAINING TUBE, DLR AND TRAM IS STILL UNVERIFIED (major). BODS was not read for this check either. Transitland attaches London Underground, DLR and London Trams to a separate feed converted from TfL data by Interline, not to the BODS feed. Treat TfL TransXChange conversion as the likely primary path until the file is inspected.

3. RAIL SOURCE AND CONVERTER DO NOT MATCH (major). NWR Schedule is confirmed 'Open (OGL3)' and the RDG timetable is confirmed 'Open (restrictions may apply)'. But gb-transit cif2gtfs is documented only for the RDG DTD feed (RJTTFxxx.ZIP), not Network Rail CIF. The licence-safe feed needs UK2GTFS nr2gtfs (R) or a small custom converter, or the RDG licence must be cleared.

4. CELL COUNT IS ABOUT 11 PER CENT LOW (minor). 0.105 km2 is the global H3 average. At London's position on the H3 icosahedron cells are about 0.094 km2, giving about 16,700 cells, 279 million pairs and 279 MB per matrix rather than 15,000 / 225 million / 225 MB.

MY VIEW ON THE MATRIX DESIGN: do not build hex-to-hex. Use origins at residential points and destinations at hexagons. Compute cost in R5 is linear in origins and almost free in destinations, origins only matter where people live, and the boundaries report already makes census units the canonical cell with population-weighted centroids. Hex centroids as origins fall in parks, water and rail land (R5 silently snaps up to 1,600 m) and need census populations disaggregated to hexes for the roll-up.

Pair counts and storage per matrix as uint8 minutes, with 16,700 destination hexes:
- A. Hex x hex (report's design): 279 million pairs, 279 MB, about 2.2 GB for 8 matrices, 16,700 searches per run.
- B. Output Area centroids x hex: 26,369 x 16,700 = 440 million pairs, 440 MB, about 3.5 GB for 8, 26,369 searches per run.
- C. LSOA centroids x hex: 4,994 x 16,700 = 83 million pairs, 83 MB, about 0.67 GB for 8, 4,994 searches per run.
- D. LSOA x LSOA (boundaries report's suggestion): 25 million pairs, 25 MB. Rejected: LSOA centroids are poor workplace destinations (City, Canary Wharf, Heathrow).

Recommendation: start with C for v1. It is 3.3 times cheaper to compute than A, works even on unparallelised r5py (my unmeasured guess of 2 to 8 seconds per origin gives 3 to 11 hours per run single-threaded), and joins the census cell table with no interpolation. Move to B if within-neighbourhood ranges look too thin at about 11 LSOAs per neighbourhood. Storage is trivial in every option. Defer the evening return matrix: its origins are the destination hexes, so it costs 16,700 searches regardless.

The two research reports currently disagree on the base cell (transit-routing: H3 both ends; boundaries: Output Areas, with LSOA centroids suggested for the matrix). This needs one decision before any pipeline code is written.

Limits of this check: no web search was made. I used pages at known addresses, GitHub raw files and release feeds. Two public Rail Data Marketplace pages were read as page text. The London H3 cell area is my calculation from H3's documented projection (it reproduces H3's published maximum cell area exactly), not a library measurement. Per-origin timings are estimates, not measurements.

## New facts
- r5py since v1.0 computes travel-time matrices one origin at a time in a plain Python loop; joblib is only used for detailed itineraries. R5's per-origin code has no internal threading. Parallelism must be added by the caller.
- r5py downloads its own patched R5 jar from github.com/r5py/r5 (v7.5.1-r5py in release 1.1.7, checked by SHA256). Upstream R5 v7.6 is only wired into r5py's unreleased main branch.
- R5 cannot handle GTFS times above 24:00:00 (r5py docs). Night services need a preprocessing step.
- R5 links any point to the street network within 1,600 m (StreetLayer.LINK_RADIUS_METERS = 1600, with a 300 m first pass). A hexagon centre in a park, reservoir or the Thames is silently moved up to 1.6 km, possibly across a barrier.
- r5py defaults differ from the report's intended settings: departure window 10 minutes, walking 3.6 km/h, cycling 12 km/h, traffic stress 3, max rides 8, max time 2 hours. R5 accepts at most 5 percentiles per run.
- H3 res-9 cells in London are about 0.094 km2 with about 190 m edges (global average is 0.105 km2). H3's published res-9 range is 0.0638 to 0.1271 km2. This is calculated from H3's projection geometry, not measured with the library.
- Transitland hosts a GTFS conversion of TfL data made by Interline (feed f-transport~for~london, file uk-tfl.zip) listing London Underground, DLR, London Trams, Thames Clippers and Woolwich Ferry; attribution 'Powered by TfL Open Data'; last fetched 2026-09-22. Useful as a cross-check or bootstrap. Download terms and whether an API key is needed were not confirmed.
- Bus data quality in BODS also needs validation. It has not been measured.
- gb-transit cif2gtfs takes only the RDG DTD timetable zip (RJTTFxxx.ZIP) and builds three months of the GB network in about 45 seconds using 5 GB of memory. UK2GTFS has a separate nr2gtfs function for Network Rail CIF.
- Release years resolved: MOTIS v2.11.3 on 2026-09-10; OpenTripPlanner v2.10.0 on 2026-09-09; R5 v7.6 on 2026-08-01; r5py 1.1.7 on 2026-06-29.
- The transit-routing and boundaries reports disagree on the base cell: transit-routing uses H3 res 9 for both origins and destinations; boundaries makes 2021 Output Areas the canonical cell and suggests LSOA centroids for an all-pairs matrix. No shared cell table has been agreed.
- London counts used in my option sizing (26,369 Output Areas, 4,994 LSOAs, 1,002 MSOAs) come from the boundaries report's count against the ONS lookup; I did not re-verify them against a primary page.
- The TfL Journey Planner timetable file is republished daily but its content is updated every 7 days and ignores planned engineering works.
- No web search was made. BODS was not read.
