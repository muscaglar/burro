# packages/pipeline

Builds Burro's data releases. It holds the licence registry and the ingest gate, the code that writes and reads a release folder, the generator of the synthetic release, the step that fetches a publisher's file, the records of evidence, the geography a figure is worked out on, the methods that work one out, the step that puts a first build together as a release and gives each of its areas a name, the step that works journeys out from a timetable, and the draft of London's named areas. It is built to [docs/design/contract.md](../../docs/design/contract.md) and [docs/design/london-data.md](../../docs/design/london-data.md); if code and design disagree, change one of them in the same commit.

Every test runs offline, on small made-up files shaped like a publisher's, and says so. A few modules of tests read the real files of the first build: `tests/cells/test_the_real_files.py`, for a measure `tests/derive/test_<measure>_on_the_real_files.py`, for the food register `tests/derive/test_food_register_on_the_real_files.py`, for the whole build `tests/assemble/test_preview_on_the_real_files.py`, and for the editions a build takes `tests/assemble/test_editions_on_the_real_files.py`. Each is skipped where `BURRO_STORE_FOLDER` names no store, and where the working copy holds no folder `data/receipts`. What each real file holds is in [docs/research/data/m1-files.md](../../docs/research/data/m1-files.md). What the files of names and borders hold is in [docs/research/data/m3-files.md](../../docs/research/data/m3-files.md).

## The command line

- A step of a build is run as `uv run python -m burro_pipeline STEP`. `--help` lists the steps in the order a build takes them: fresh, plan, fetch, by-hand, receipts, held, describe, seal, cells, travel, draft, preview, check, coverage, keep, take, moved, why. It is the one way in: the Makefile and the hosted workflows run the same commands, and `tests/test_command_line.py` holds both to the arguments each step takes.
- A step is owned by the part that does the work: `fetch/cli.py`, `evidence/cli.py`, `cells/cli.py`, `areas/cli.py`, `assemble/cli.py`, `kept/cli.py` or `upkeep/cli.py`. It is a `Step` in that file's `STEPS`, with what it does, examples and exit codes. An example is parsed by a test, so it cannot go stale.
- A step's help says whether it reaches a network. Only `fetch` reaches a publisher.
- On standard output a step prints lines of `key=value` that `tools/public_log.py` lets through: step names, registry ids, counts and hashes. Words go to standard error, on one line: what is wrong, what a person can do about it, and the rule's name. Neither holds a row, a key, an address or the name of an area, and neither repeats what the step was handed from a file.
- `tests/walk/` walks the whole of a build on made-up files and breaks each link in turn. A new step joins the walk. `cells` and `preview` have not joined it yet: their own tests walk each from a store to the hash of a file, and `tests/assemble/` breaks the links of a whole build.

## The registry

- Every step that reads external data starts with `Registry.require(source_id, use)`. No exceptions, including one-off scripts and notebooks.
- Rules live in `src/burro_pipeline/registry/rules.py`, one small function each, listed in `ERRORS` or `WARNINGS`. A new rule needs a case in `tests/test_registry_rules.py` that shows it catching a violation.
- `load()` refuses a registry that breaks an error rule, so the gate never answers from a bad one. Only tools that report problems pass `enforce=False`.
- `Source` is frozen and rejects unknown fields, so a typo in a registry file fails loudly.
- Tests never touch the network. Use the fixture registry in `tests/test_registry_gate.py`.
- What the terms of a publisher ask to be said wherever its credit is shown is held in its entry, under `said_with_attribution`: in plain words, what the terms ask and no more. The credit itself stays as the publisher worded it, and is never changed to hold it. `sources_of` in `assemble/release.py` carries it to the release with the credit, and `check` holds a release to it as it holds it to the credit, under `credit_is_the_registrys`. A release of which nothing is asked does not hold the field, and is byte for byte what it was. The two sources of the Greater London Authority hold one, which the terms of the London Datastore ask for.

## Releases

- `write_release` is the only way a release reaches disk. It checks every source a real release cites against the registry, for the use its file needs, before it writes anything. It never writes over a real release.
- `read_release` reads the bytes and leaves all the checking to `open_release` in core, so the pipeline and the API cannot disagree about what a valid release is. Do not add a check here: add a rule in core.
- `read_served` reads a release as it may be served: with the folder beside it, through `open_served` in core, as the API does. `burro-release check` reads it so, and then holds every fact of a release that is not made up to its row of evidence: the row must be there, hold the same figure, name the method of its measure and rest on the one file the code reads the measure from. A measure whose publisher cuts its product to squares of the grid says so in `derive/measures.py`, and its row may rest on the file of each of several squares, and on no other file of the source. A measure whose publisher gives a file for each part of the whole says so too, as `in_parts`, and its row rests on the file of every part that the lock names: a row that names some of the register's files and not all is found.
- A refusal is one line: the folder, the file, the row, what is wrong in plain words, and the rule's name. It never repeats a value from the file. A new rule in core needs its words in `MEANING` in `release/read.py`.
- A folder holds the release's files and nothing else. A stray file, a hidden one included, is refused. The one exception is a file named exactly `.DS_Store`: `read_release` leaves it out and never opens it, and `write_release` leaves it where it is. Do not add a second exception without a decision.

## The synthetic release

- `release/synthetic/` reads nothing: no file, no dataset, no network. That is why it has no `Registry.require`, and a test checks its imports. Keep it that way.
- It is unmistakably made up. Every name is invented, every id begins `syn-`, the map is in open sea, and the manifest says `synthetic`. `tests/test_synthetic_release.py` holds a list of real names and fails if one appears.
- That list is London's best-known names and the names that were once used here and found to be real. It is not a gazetteer, and none has been consulted: on 2026-09-23 every name was looked up in one encyclopaedia, which does not cover a small street, a farm or a hamlet. Make a new name from a word that is no part of any place name, and say in the change whether it was looked up, and where. A name that replaces another must sort where the old one did: ids are given in name order, and an id never moves. Add the old name to the list in the same change. A second test looks for every name on it in every file of code and of tests.
- An alias is a name. "Moot Hall" alone is what real buildings are called; "Tallowgate Moot Hall" is not. Give an alias the name of the place or of the borough before it.
- No time in the release is under 2 minutes. `whole_minutes()` in `journeys.py` is the only place a time is rounded; use it for any new time.
- The character of each area is set by hand in `names.py`. The seed only moves figures a little. A test that says which area a spec should find must hold for other seeds too, or it is testing luck.
- The city keeps its made-up names. Beside each stands a made-up label, the borough and the number of the area, as a publisher labels a census area, and each name says that it is a draft or that it was checked: `CHECKED` and `NOT_NAMED` in `names.py`. Two areas bear no name but their label, so that what is shown of one is tested. No figure moves with any of it.
- No two vibes find the same areas, or nobody could tell what one adds to another. No two ends of two vibes share more than three of the first five areas each finds, and no two vibes have a rank correlation above 0.8 across the areas, either way. `tests/test_synthetic_vibes.py` holds both, on the committed seed and three others, and `APART` there names the areas that break each pattern: flats that are quiet, a leafy area on a main road. A trait that is moved can bring two vibes together, so run the tests after any change to the plan.
- Asked for alone, each end of each vibe puts an area of its own first. `ENDS` in `tests/test_synthetic_vibes.py` is the table. The one exception is held there too: Going out towards Buzzy and Houses or flats towards Flats both find the centre. A change to a figure that moves a row of that table is a change to the city, so say it.
- Three areas are mixed by hand, one on each scale that both ways of gritty carry: `MIXED` in `build.py`. Every other spread is the band itself.
- It draws only from `Random(seed).random()` and uses no arithmetic that differs between machines: `sqrt`, never a fractional power.
- Adding a feature moves no figure that was there. A new feature draws from a stream of its own, `Random(seed + 1)`, and the traits `offices` and `works` are read by the newer features only. A test holds the 23 features of the first catalogue to one digest. A change to the plan of an area is another matter: it moves the figures of that area, its costs among them, and the digest. Say so in the change, and say which named cases moved. The map, the journeys, the stations and the places do not read the traits, and never move with them.
- Gritty is one vibe, which counts recorded crime, and Works and warehouses is a part of it (ADR 0013, as amended). The committed release carries Gritty, serves no vibe of the name Works and warehouses, and says `b`. A release that holds no recorded crime and carries no Gritty says `a`, and carries Works and warehouses in its place: it is built on demand, `burro-release build-synthetic --gritty a`, under an id of its own, and is never committed. Which of the two is built moves no figure. What is recorded is drawn to follow the night and the middle of town more than the works, so that Gritty is not the works under another name.
- `data/fixtures/synthetic/` is generated. After any change to the generator run `make fixture` and commit the result. A test fails if the committed files are not what the generator makes.

## The file of changes

- `changes.py` is the one reader of a file of changes: what a person decided at the panel of the review desk, one line for each change, with who made it, the day, what stood before, what stands now and why ([the design of the panel](../../docs/design/panel.md), section 3). The desk writes a line with `line`, and reads the file with `read`, as a build does. Do not write a second reader.
- `preview --changes FILE` reads the file whole before the store is looked for. A line that cannot be read, a change that breaks a rule, and a change that was made of something other than what stands each stop the build, and nothing is written. The refusal names the line by its number and the rule by its name. **It never prints what a line holds**: a reason is a person's own words.
- What stands is laid over core's own by `adjusted` and `relabelled`, and held to core's rules there, so that a change that cannot be served stops the build before a file is opened. Every band is worked out with the recipe the release then carries: `tag_raw` is handed it.
- `preview --published-changes FILE` is for a build that no person starts by hand, as a hosted run is. It is given the place the desk publishes the founder's file to, whether or not anything was published. Where the repository tracks a file there, it is taken as `--changes` takes one and held to every rule of it. Where the repository tracks none, the build is given none and is byte for byte what it is with no file. What stands there and is not tracked is never read, and stops the build. `_published` in `assemble/cli.py` is the whole of it, and `evidence.repository.tracks` says what the repository tracks: whether there is a file is never the workflow's to ask, because a step a run may leave out is a step a run may be made to leave out. `tests/assemble/test_published_changes.py` holds each, and `tools/tests/test_the_build_of_london.py` holds the workflow to the place.
- The lock names the file by its hash, as `changes/<name>`, and `build.json` lists each line that was applied by its number, with no reason. **With no `--changes` a build is byte for byte what it was**: nothing is added to the lock, to the record or to the release. `tests/assemble/test_preview_with_changes.py` holds each.
- A chain that was moved to another tier, added or taken out is laid over the table of tiers by `table_with`, and the measures of the chains are worked out by that table, for that build alone: `brand_table.using` sets it and puts the repository's back. `brand_tiers.toml` is what a build starts from, and no build writes it. `tests/derive/test_brands_with_changes.py` holds each.
- A kind of line that no build applies yet stops the build: it is never passed over. A flag is for a person, and a build does nothing with it.
- **The file can be written by hand, so every limit is held here and in core, and none in the panel alone.** A build takes the founder's file, `r1.jsonl`, and only as the repository holds it at the commit that is checked out: `evidence.repository.holds` reads git's own files. A chain of the table is moved by its tier alone. A chain that is added is named as the file of places writes it, and is added only where that file gives the name to two places or more that stand apart: `seen_to_be_a_chain` says how a chain is told from a person and from one shop, and that it cannot be told any other way. `tests/assemble/test_changes_written_by_hand.py` holds each, and `tests/assemble/published.py` makes the repository a test builds from.
- No figure of a place is in the file, and none is ever read from it. A figure is a publisher's.

## Household income, which is shown beside a release

- Household income is no file of a release and no measure. `derive/household_income.py` reads the statistics office's workbook for `display`, which is the one use of it a build may ask for: the registry lists no scoring for it, and the gate refuses it for a feature or a cost. It is on no list of measures, makes no row of a catalogue or of evidence, and works out no percentile. Do not add it to `MEASURES`, and do not hand a figure of it to `assemble/release.py`.
- `preview` writes it to a folder of its own beside the release, named for it with `-income` after, through `write_income` in `release/income.py`, where a list of the build names the workbook and it has a receipt. It prints one line, `step=income`, with counts and no figure. `open_income` in core is the only judge of the folder.
- The step holds the workbook to the sentences an area's page quotes of it: the year, that the estimates are model-based, the definition of the kind of income, and the credit. A workbook that lacks one stops the build. So a new edition is read only once core's words are its words.
- The made-up estimates are `release/synthetic/estimate.py`. They are drawn from noise alone, from a stream of their own, and follow no trait of an area. They are committed at `data/fixtures/income/`.

## The census of a release

- A census is no file of a release. It is written to a folder of its own, named for the release with `-residents` after it, by `write_census` in `release/residents.py`, and `open_census` in core is the only judge of it. Do not give a release a file for it, and do not let a step that builds what is ranked import it: `tests/test_residents.py` reads the imports.
- The gate of a census is the one use `census_table`. `write_census` asks it of every source of a census that is not made up, and refuses a table the entry of its source does not name. No step reads a real census table yet.
- The made-up count is `release/synthetic/count.py`. It reads nothing, and draws from a stream of its own, `Random(seed + 2)`, so it moves no figure of the release. Its three tables of groups name no real group, religion or country, and follow no trait of an area. Do not give one a real heading: a test holds the headings of the three real tables.
- It is committed at `data/fixtures/residents/`, and never under `data/fixtures/synthetic/`, which holds releases and nothing else: more than one tool takes the one folder it finds there for the release. `make fixture` rebuilds both.

## Fetch

- `src/burro_pipeline/fetch/` is the only part that may reach a network, and in it only `download.py` and `s3.py`. `tests/fetch/test_only_fetch_reaches_a_network.py` reads every module of the pipeline and of core, and holds the list of packages they may import. A package you add goes on that list, with its reason in the change.
- The gate of fetch is `ask` in `fetch/gate.py`, and `plan`, `fetch` and `by-hand` all go through it. It asks `Registry.require`, and then holds the file to the entry of its source: its page is the entry's own address or one of its evidence addresses, its address is one the entry names for its files under `file_urls`, and nothing that says what the file is names a census table about residents. A publisher serves many datasets from one host, so the host of an address is not enough: `registry/README.md` says what an entry needs for a file of its to be fetched. What such a table is, is asked of the registry's own rule: fetch holds no list of tables and no pattern of its own. Never call `Registry.require` alone in fetch.
- The order is fixed: the gate is asked about every file of the list before anything is asked of a publisher, and again as the first thing done for each file. One refusal stops every download, whether or not the file that was refused was asked for. What arrived is held too, before it is kept: the address a request ended at, the publisher's name for the file, and the names inside a zip and inside every zip it holds. A zip that cannot be looked into is refused with `why=19`.
- A store is of one part: the product, the census tables about residents, or the audit. Only the product's can be named. So a file that is read for the audit, or is a census table about residents, is refused with `why=15`. That refusal is the whole of what is built for them: do not add a way round it.
- A list of files is data, in `fetch/lists/`. It holds the page a person finds a file on, from the registry entry, and the file's own address once a person has found it. Never make an address up. What nobody has checked is named under `unsure`. An edition and a period stay there until a person has read them in the file as a fetch stored it, so the first fetch of a file writes no receipt: `tools/tests/test_guide.py` holds the first list to it, and `docs/data-builds.md`, section 7, says how a receipt is then written and how one that is wrong is put right. The eleven files of the first list are named there as read: a program read each, and no person has, and whether that stands is the founder's to decide. An address holds no parameter but those the list names under `url_parameters`, and no other is written in a receipt, and each only with the value the list's own address gives it: a list and a receipt are both committed where anyone reads them.
- A file is kept under its hash and is never written over. A receipt is written last, and only from an edition and a period that the list is sure of, or that fetch read in the file where the list says. The first receipt of a file stands. A copy of it is kept in the store beside the file, because a hosted run writes to a disk that is thrown away. Before a receipt is written, the copy in the store is read back and compared. If it says something else the file ends `differs`, and the run ends red.
- Fetch writes the edition a list states on whatever arrives. So a list states no edition for a file whose publisher names none and replaces it under one address. It says under `edition_from` where the file states its own, and `fetch/dated.py` reads that in what arrived, before anything is kept: the day in a named element of the header of an XML file, the day a GeoPackage says its contents were last changed, the time the first block of a street extract says its data runs to. It reads that one value and nothing else of the file, and what it gives is a day or a time and never text. A file that holds no date has the day it was retrieved for its edition, from fetch's own clock. A list may not state an edition and say that the file states its own.
- The receipt says where its edition was read, under `edition_from`. A receipt of an edition that a page stated does not hold the field. A day that is about the file and not about its data is never the period of its data. So fetch takes the day a GeoPackage was last changed for an edition alone, and the list states the period. A boundary is as the file holds it: where neither the file nor a page states a day its outlines are as at, the list states the day the file was last changed, and its notes say why and what that day does not say, as the list `m2-places` does of the town centres. A new kind of file that dates itself gets a value of `Where` in `evidence/receipt.py`, a reader in `fetch/dated.py`, and tests on made-up files of the real shape in `tests/fetch/test_the_day_a_file_gives.py`.
- One edition is one file. The same bytes fetched again change nothing. New bytes that state a new edition are a new file with a receipt of its own, beside the old. New bytes that state the edition of a file of the same item that has its receipt are refused with `why=35`, and nothing is kept. A file that does not state its edition where the list says is kept with no receipt, `why=34`. `tests/fetch/test_a_file_that_states_its_own_edition.py` holds fetch to each, and `tests/fetch/test_editions_a_file_gives.py` holds the two lists to what they say of 37 files.
- Do not open a file with no receipt, in a test or in a script. The 37 files were fetched before fetch read an edition. 36 have a receipt since they were fetched again: the 33 of the food hygiene register, two reports and the town centres. The street extract has none. The drafting of the areas can read a file that has none, through `names_files.without_receipt` and `context_read.take`, for a draft alone and with everything that rests on it marked `no_receipt`: the sections on areas below say so. It read the town centres so until they had their receipt, and reads no file so now.
- `seal` and `preview` pair a receipt with an item by the edition and the period the list states. An item that states none, and says where the file states its own, is paired by the rule at the top of `evidence/lock.py`, and `take` there is the one place that applies it. A receipt is of the item when fetch could have written it from the item: its source, its use, the list's own address, the place the edition is read in, and an edition that is the list's words and a day. A build takes the edition it is told to with `--edition ITEM=EDITION`, or the newest by the day the file states, and never by the day a file was retrieved or the order of a folder. Two receipts of one item that state one edition stop the build. Do not add a second way to choose, and do not choose anywhere else.
- The lock says what was taken of such a file: `item` and `edition`, beside the hash. It leaves both out for every other input, so a lock of files whose editions the list states is the bytes it always was. A build that is told the editions a lock names seals that lock again. How an edition was chosen is printed and is in no file, or the same files would seal to two locks.
- What goes wrong with one file is said of that file, with a number of its own in `Why`, and the run goes on to the next. `WORDS` says what each number means and what a person can do about it. A fault that is of no one file stops the step with exit code 3.
- The receipt is the one in `evidence/receipt.py`. It holds the address the list gave, as `listed_url`, beside the address the file came from in the end. Fetch defines no record of its own, and works out no key or path of its own: `tests/fetch/test_one_record.py`.
- Where a request ended is held by `hold_where_it_ended`. An address that cannot be read one way only is refused on any host, and an address is another entry's however a server may have read it. Reading an address more ways may refuse more, and never allows more.
- A download never follows a redirect to a host the list does not name, never reads a proxy, a cookie or a login from the machine, and refuses an address that is not public or that holds a letter outside ASCII. A test reaches the loopback address only, behind `loopback_for_tests`.
- One store is named by the environment: a folder or an object store, and never both. Its address and its keys appear in no file, no error and no line that is printed. `fetch`, `by-hand`, `held` and `receipts` say which kind of store they were given, in their first line. `describe` prints JSON, and says it in the last field, `store`.
- `held --receipts FOLDER` holds the store to the receipts. Of each receipt it asks what `seal` asks of a listing: whether the store holds the file under the key the receipt gives, at the size it gives. It says list by list which file is missing or differs, reads no file, and writes nothing to the store. It names a file by its list and its item, which are names the lists of this repository give and hold nothing from a file. It pairs a receipt with an item as a build does, and `tests/fetch/test_cli.py` holds the two together: do not add a third pairing. The workflow `data-held` runs it and no other step. Its environment holds no contact, so no step of it can fetch.
- A line holds only names that are on the list in `tools/public_log.py`. Add a new name there in the same change. What arrived in place of a file is said as `kind=` and one word of `Kind`, and a test holds the list there to it. A host is never printed by name: `host=` is followed by twelve digits of a hash of it, and `plan --words` prints the same beside each host it knows.
- A list may say under `take` which part of a Parquet file to take: a box, the column that holds the box of each row, and the columns. `fetch/parquet.py` reads the footer with the standard library alone, `fetch/take.py` works out which bytes the part is, and `InPieces` in `download.py` asks for them, a piece at a time. What is kept is the publisher's own bytes, run after run, and never a file written again: the receipt says under `taken` which file, which row groups and which runs, so the same part taken again is the same bytes. A row group is taken whole or not at all, so a part holds rows outside the box. Do not unpack, filter or rewrite what arrives in fetch. A publisher that gives no pieces is `why=36`, a file that changes on the way `why=37`, and a file that is not laid out as the list says `why=38`. `tests/fetch/parquet_support.py` writes the made-up file with a Parquet library, so that the reader of footers is held to a real writer.
- A part is not a Parquet file: a footer says where a column lies in the whole file. A step reads one through `TakenFile`, which refuses a read of a byte that was not taken and never answers it with nothing. Hand a Parquet library the footer by itself first, and tell it to read each column by itself: left to itself it asks for the columns of a row group in one piece, with what lies between them.
- `describe` prints names from a file's own layout, for a person's own machine. It takes the first full row of a table for the names of its columns, and prints no names where it can tell that row to be data. It cannot always tell, so what it prints is treated as if it held a row: no workflow runs it, and `tools/check_data_workflows.py` refuses one that does. Of an OpenDocument workbook it gives, with `--sheet`, the words of the one sheet that is named: each row that holds words alone, as a cover, notes and the title over a table do, and never a row that holds a number. `fetch/opendocument.py` reads it. Of a GeoPackage `describe` gives the day each layer says it was last changed, as a day and as nothing else. It is how the day is read that a list states as the period of a file of boundaries, before the file has a receipt. Of a timetable in TransXChange `describe` gives the days its services say they run from and to, and the mode of each: `fetch/timetable.py` reads those three places of each service, as a day or as one word and as nothing else, and stops where the services end. It is how the period of a file of timetables is read before the file has a receipt. With `--inside` `describe` looks into a zip inside a zip, as many zips down as fetch looks before it keeps a file.
- The list `m5-journeys` holds the one file of a journey that no other list holds: the timetables of Transport for London. No page its entry holds names an address for it, and no timetable is given to a person who has not registered. Its address is the one the publisher's staff wrote on its own forum, and the entry names a second that a request may be sent on to. The zip the publisher's page links is an example that is not updated: no entry names it, and a file that arrives from it is refused. A fetch took the file on 2026-09-24, with no key: a zip of six zips, which hold 826 timetables in TransXChange. The list states its edition, the day in the names of the six zips, and its period, the days its services say they run on, as `describe --inside` gave them. The file is replaced each week under one address, and a list's edition is written on whatever arrives: read the next issue with `describe --inside`, and state its edition and its period, before a fetch that would take it. Not every timetable runs on every day of the period, and one of the six zips holds buses that run in place of a train: the design says what that asks of the step that routes. `tests/fetch/test_the_list_of_journeys.py` holds the list to the registry. A list is offered by the fetch workflow by name, so a new list is added to `data-fetch.yml` in the same change. [The design](../../docs/design/london-data-timetables.md) says what each publisher's pages said, and what a person signs up for.
- The list `m12-household-income` holds one workbook, which describes residents. Its entry allows it to be shown and to be checked against, and the gate refuses it for a score: `tests/fetch/test_the_list_of_household_income.py` holds both to that. ## Reading a file in a build

- A step that works a figure out never opens a file by its path. It asks `Inputs.open(source_id, use)` in `inputs.py`, and is handed a checked copy with its receipt. The gate is asked first, for the use the step puts the file to. Nothing is written to the store.
- Say which file of a source is meant, with `edition=` or `named=`. The folder of receipts holds the receipts of every list, so a source may have several.
- A source that gives a file for each part of the whole, as the food hygiene register gives one for each authority, is opened with `Inputs.open_each(source_id, use)`. It hands over every file of the source that the step was given, in the order of the publisher's names. A step never picks one of two editions of a file: two receipts of one name are refused. In a build the step is given the receipts the build took. Outside one, give `Inputs` what `of_the_list` in `assemble/cli.py` gives for the lists that are meant.
- A figure that rests on several files of such a source rests on several days: each file of the register states the day of its own extract. `period_of` gives the span, and the span is what is shown as the date of the figure.
- Read a table with `Opened.text` and `Opened.rows`, and name the columns that are read. A row holds those columns and no other, so a step cannot use a column it did not name. A file with a sheet or a column about residents is read for the columns the registry allows, and the rest is never opened.
- A file that is not laid out as the step expects stops the step: `input_is_as_described`, with a few fixed words that say which. The words repeat nothing from the file.
- `Inputs.opened` is every file a step was handed. A row of evidence names those and no other.
- **No socket is open while a file is read, whatever the store is.** A store that is a folder hands a file over as it is asked for. An object store is reached over a network, so a step calls `Inputs.copy_out()` before it refuses sockets: every file of its receipts is copied out, checked against its receipt, and read from the copy. A file that is kept apart is never copied out. `--work` keeps the copies, so a draft and the build that follows copy each file once. The step prints how many files it copied, and no name of one.

## Derive

- `derive/methods.py` holds the named methods of section 5 of the pipeline design, once. A measure's own module reads its publisher's file and calls one. Do not write a second copy of a sum or a mean.

- Nothing is filled in. A unit with no figure adds nothing and lowers the coverage. Below half the homes covered the value is not given. A count of nought is a count.
- A share is one sum over another. A mean of rates is taken only by `lsoa_value_by_homes`, for a rate its publisher gives with no top and bottom, and the figure is marked as averaged.
- Where the publisher's file holds a row for the area itself, the figure is read from that row, by `area_row_ratio`, and is not added up from the rows of smaller areas. While an area is an MSOA the three measures of homes do so: the row is rounded once, and it is the number a reader finds in the publisher's table. - `kept/` is what stands between a build and an image. `keep` sends a release that was built to the store of releases. `take` brings back the one release whose lock is committed, and holds every file to it. [ADR 0030](../../docs/adr/0030-a-release-is-kept-approved-by-its-lock-and-carried-in-the-image.md) says why.
- **The store of releases is not the store of publishers' files.** It is named by `BURRO_RELEASES_FOLDER`, or by `BURRO_RELEASES_ENDPOINT` with its bucket and key, and never by a name that begins `BURRO_STORE_`. `keep` and `take` read no name of the other store, and no other step reads a name of this one. Do not give a step both.
- A file is kept under `releases/`, then the folder the build wrote it in, then its own name. `key_of` refuses any other name. A file that is kept is never written over: `keep` sends a file only where none is, and a file that is there and differs refuses the whole release before anything is sent.
- **The lock of a release is `kept/lock.py`, and `tools/release_lock.py` is the same record in the standard library.** The tool writes the lock in a hosted run and holds an image to it, where no package is installed. The two are held together by a test that reads what one writes with the other. Change both in the same commit.
- A lock holds ids, hashes, sizes, counts and the names of rules. It holds no figure and no name of a place, and a test reads every lock the repository holds for one. A lock is committed under `data/approved/`, named for its release, by the founder and by nobody else. Never write one there, never change one, and never commit a release.
- `take` takes a release of London only by a lock that is committed. With no release named and no lock in the folder it copies the made-up city and reaches no store. It removes what it wrote when a file differs, so a folder it leaves is a folder that was checked.
- `keep` and `take` open the release as the service does, with `read_served`. Neither reads household income: what stands beside a release is held to the lock by its bytes, and to its rules by `burro-release check`, which a hosted run runs first.
- What each prints is a line `tools/public_log.py` lets through: `step=keep` or `step=take`, a status, counts and the hash of the lock. It names no file of a store and no place.

## Upkeep: what is held and how old it is, and what moved between two builds

- `upkeep/` is what a person runs to keep a city up to date. `fresh` says of every file that has a receipt how long ago it was retrieved, against how often its publisher says it changes. `moved` says what differs between two releases, before the newer is approved. [The guide to refreshing London](../../docs/refreshing-london.md) says when each is run, and [the guide to adding a city](../../docs/adding-a-city.md) lists every place where London is written into the code of the pipeline: a place that is added or taken out is added to it or taken out of it in the same change, and `tools/tests/test_guides_to_a_city.py` holds the two together.
- **`fresh` reads the registry, the lists and the receipts, and nothing else.** It reaches no store and no publisher, so it never says that a newer edition is out. Due means that it is time to look. Do not make it ask a publisher: only `fetch` reaches one.
- **It reads no clock.** The day is given with `--on`, and the registry is loaded with no rule asked, because a rule of the registry reads the day. A test reads both modules for a call that asks the time.
- A receipt is paired with a file of a list by `paired` in `fetch/cli.py`, as `held` pairs them. Do not write another pairing.
- How often a publisher says a file changes is read by `registry/cadence.py`, from the first words of `cadence` and from nothing after them. A word it does not know is added to `WORDS` there, with a case in `tests/test_registry_cadence.py`. Do not read a rhythm from the middle of a sentence: an entry that cannot be read is put right in the registry.
- A file whose cadence is not said is never called fresh, and a file that changes rarely is never due by its age. `STATES_NONE` in `tests/test_registry_cadence.py` names the entries that hold a receipt and state no rhythm: an entry joins it only where its publisher states none.
- A line holds ids, a day, counts and words of the fixed lists in `tools/public_log.py`. The edition and the period of a receipt are what a file or a list said, so they stand in the table of `--table` alone, which is for a person.
- **`moved` reads each release as it is served**, through `read_served`, so a release that would not be served is not compared. It works nothing out again but the difference: a band and a rank are core's, and a search is ranked by `upkeep/searches.py`, which the panel of the review desk ranks it by too. Do not write a second copy of either.
- **`moved` prints counts, and names an area only in what it writes.** A line holds ids of the catalogue and of the registry, the ids of the two releases and counts. The name of an area, its id and a figure of one are in `moved.json` and `moved.md` alone, which `upkeep/written.py` writes to the folder `--out` names. That folder is one git ignores, or one outside the repository: `may_be_written` refuses any other. Never print a row of what was found, and never commit what was written.
- A step between two figures is the difference a person finds by hand, worked out in decimals. The step in the middle is the lower of the two in the middle, so that it is a step an area took. Do not average two steps.
- The files behind two builds are compared from their two locks. A receipt says which file of which list an input is, and which edition: `paired` pairs them, as `held` does. With no receipt, a file is known by its id alone, and a file that changed is said to have gone and another to have come. A made-up release has no lock, and no file of it is compared.
- What is written holds no sentence that a person typed. A search is named by its id, its name and how it was read, and `searched` leaves the sentence out. The panel adds the sentence for its own screen, on the machine of the person who decides.
- The panel draws what `compare` gives, through `routes.moved_since` of the desk. A field that is added to what `compare` gives is a field the page may read: change the page and its test in the same change.
